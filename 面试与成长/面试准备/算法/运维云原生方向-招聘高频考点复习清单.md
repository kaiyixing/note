### 模块 1：Linux 操作系统 ⭐⭐⭐（100% JD要求）

**JD 原文摘录：**
- "精通 Linux 操作系统，具备扎实的系统管理、网络排障、性能分析、Shell/Python 脚本编写能力"（猎聘-高级云运维）
- "深入理解 Linux 操作系统，熟练掌握常用命令、性能分析工具（top/sar/perf/strace 等）和系统调优"（腾讯-边缘基础设施运维）
- "扎实的 Linux 基础（CentOS/Rocky/AlmaLinux/Ubuntu），熟悉进程、内存、I/O、网络的性能分析方法"（51job-云运维）

**必背面试题：**

#### 1.1 系统基础
- [ ] **Linux 启动流程**：BIOS/UEFI → MBR/GPT → GRUB → Kernel → systemd → 运行级别(target) → rc.local
- [ ] **7种文件类型**：`-`(普通) `d`(目录) `l`(软链接) `b`(块设备) `c`(字符设备) `p`(管道) `s`(socket)
- [ ] **硬链接 vs 软链接**：硬链接=同inode多文件名，不能跨文件系统；软链接=独立inode指向路径，可跨文件系统
- [ ] **CentOS6 vs 7+ 开机自启**：6用 chkconfig + /etc/init.d 脚本；7+用 systemd unit 文件 + `systemctl enable`
- [ ] **LVM 三概念**：PV(物理卷) → VG(卷组) → LV(逻辑卷)；在线扩容：加盘→fdisk→pvcreate→vgextend→lvextend→xfs_growfs/resize2fs
- [ ] **RAID 级别**：0(条带化,高性能无冗余) / 1(镜像,100%冗余) / 5(奇偶校验,至少3盘) / 10(先镜像后条带)

#### 1.2 性能排查（面试必考"线上出问题了怎么排查"）
- [ ] **CPU 高排查**：`top`/`htop` → `ps aux --sort=-%cpu` → `top -Hp <pid>` 找线程 → Java用`jstack`，通用用`strace -p <pid>`看系统调用，`perf top`看函数级热点
- [ ] **内存高排查**：`free -h` → `ps aux --sort=-%mem` → `pmap -x <pid>` → `dmesg | grep -i oom` 查OOM
- [ ] **磁盘IO高**：`iostat -x 1`(看%util、await) → `iotop` → `df -h`/`du -sh *` → `lsof +L1` 找已删除但被占用的文件
- [ ] **du vs df 不一致**：有进程持有已删除文件的句柄，文件未真正释放。`lsof | grep deleted` 找到后 kill 对应进程或重启服务
- [ ] **网络连接排查**：`ss -s` 总览 → `ss -tunlp` 查端口占用 → `ss -ant` 查连接状态 → `netstat -nat | awk '{print $6}' | sort | uniq -c` 统计连接状态
- [ ] **系统负载**：`uptime`/`w` 看 load average（1/5/15分钟），load > CPU核数说明过载
- [ ] **腾讯JD特别提到的工具**：`top`、`sar`、`perf`、`strace` —— 中高级岗必须会用 perf 和 strace

#### 1.3 常用命令（必须熟练到能手写）
```bash
# ===== 日志分析 =====
# Nginx访问量TOP10 IP
awk '{array[$1]++} END{for(ip in array) print ip, array[ip]}' access.log | sort -k2 -rn | head -10
# 查错误日志
grep -i "error\|exception" /app/logs/*.log
tail -f /var/log/nginx/error.log

# ===== 查找 =====
find /var/log -type f -name "*.log" -mtime +30 | xargs rm -f   # 删30天前日志
find / -size +100M -type f 2>/dev/null                            # 找大于100M文件
du -sh /* | sort -rh | head -10                                    # 找占用最大的目录

# ===== 进程/端口 =====
ss -tunlp | grep :80          # 查80端口被谁占用（比netstat快）
ps aux | grep nginx            # 查进程

# ===== 定时任务 =====

# 格式：分 时 日 月 周 命令

```

### 模块 2：Kubernetes ⭐⭐⭐（90% JD要求，云原生核心）

**JD 原文摘录：**
- "精通 Kubernetes 架构及生态工具（如 Etcd、Calico、Istio、volcano），具备集群性能调优经验（如 APIServer 负载均衡、节点调度优化）"（BOSS-云原生运维）
- "熟悉 Kubernetes、Docker、容器网络、Ingress、Service、资源调度、滚动升级、故障排查和集群运维管理"（猎聘-高级云运维）
- "精通 Kubernetes 核心原理及组件（kube-apiserver、etcd、scheduler、controller-manager），熟练掌握容器、镜像、PV/PVC、资源配额、污点容忍等核心机制"（上海AI实验室-SRE）
- "熟练掌握 Kubernetes 核心原理与运维，有大规模集群管理经验（50+ 节点）"（腾讯-边缘基础设施运维）

**必背面试题：**

#### 2.1 集群架构组件（必考）
- [ ] **Master 节点组件**：
  - **kube-apiserver**：所有操作的统一入口，REST API，认证鉴权，水平扩展
  - **etcd**：集群分布式KV数据库，存储所有集群状态，**必须做备份**
  - **kube-scheduler**：Pod调度器，根据资源/亲和性/污点等决定Pod放到哪个Node
  - **kube-controller-manager**：运行各种控制器（Deployment/Node/Job/Endpoint等）
- [ ] **Worker 节点组件**：
  - **kubelet**：Node上的agent，管理Pod生命周期，与apiserver通信
  - **kube-proxy**：网络代理，实现Service的负载均衡（iptables/ipvs模式）
  - **容器运行时**：Docker / containerd / CRI-O（K8s 1.24+ 默认 containerd）

#### 2.2 核心资源对象（必考）
- [ ] **Pod**：最小调度单元，一个Pod可含多个紧密耦合容器（共享网络命名空间和存储卷）
  - 状态：Pending → Running → Succeeded / Failed / Unknown
  - 重启策略：Always（默认）/ OnFailure / Never
- [ ] **Deployment**：无状态应用管理，管理ReplicaSet，支持**滚动更新**和**回滚**
- [ ] **StatefulSet**：有状态应用（数据库等），稳定的网络标识（pod-name.service-name）和稳定持久存储
- [ ] **DaemonSet**：每个Node运行一个Pod（日志采集agent、监控agent、网络插件）
- [ ] **Job / CronJob**：一次性任务 / 定时任务
- [ ] **Service**：Pod的服务发现和负载均衡入口
  - ClusterIP（集群内部访问，默认）
  - NodePort（通过NodeIP:NodePort暴露，范围30000-32767）
  - LoadBalancer（云厂商LB，自动分配外网IP）
- [ ] **Ingress**：七层HTTP路由，域名/路径规则转发到Service，常用Nginx Ingress Controller
- [ ] **ConfigMap / Secret**：配置管理 / 敏感信息（Secret是Base64编码，非加密）
- [ ] **PV / PVC / StorageClass**：持久化存储
  - PVC = 用户申请的存储属性（大小、读写模式）
  - PV = 实际存储卷（NFS/Ceph/云盘等）
  - StorageClass = 动态供给PV的模板，指定Provisioner
- [ ] **HPA（Horizontal Pod Autoscaler）**：基于CPU/内存/自定义指标自动扩缩容Pod副本数

#### 2.3 调度与资源管理
- [ ] **requests vs limits**：
  - requests = 调度时保证分配的最小资源（节点筛选依据）
  - limits = 运行时最大使用上限（CPU超限被限流throttle，内存超限被OOMKill）
- [ ] **三种探针（Probe）**：
  - **livenessProbe**（存活探针）：失败则kubelet重启容器
  - **readinessProbe**（就绪探针）：失败则从Service Endpoints摘除，不接收流量
  - **startupProbe**（启动探针）：慢启动应用专用，成功后才开始liveness/readiness检测
  - 探针类型：Exec（执行命令，退出码0=成功）/ TCPSocket（端口能连通）/ HTTPGet（HTTP响应码2xx/3xx）
- [ ] **污点(Taint)与容忍(Toleration)**：Node打污点（key=value:effect），Pod必须声明对应容忍才能调度上去；effect有 NoSchedule/PreferNoSchedule/NoExecute
- [ ] **亲和性调度**：nodeAffinity（节点亲和）/ podAffinity（Pod亲和，放一起）/ podAntiAffinity（Pod反亲和，分散开）
- [ ] **资源配额(ResourceQuota)**：命名空间级别的资源总量限制
- [ ] **LimitRange**：命名空间内单个Pod/容器的默认和最小最大资源限制

#### 2.4 网络原理（中高级必考）
- [ ] **Pod间通信**：
  - 同Node Pod间：通过CNI网桥（如cni0/docker0）直接转发
  - 跨Node Pod间：通过CNI插件实现（Flannel用VXLAN隧道，Calico用BGP三层路由）
- [ ] **Flannel vs Calico**：
  - Flannel：VXLAN叠加网络，配置简单，不支持NetworkPolicy网络策略
  - Calico：BGP三层路由（也支持IPIP隧道），支持NetworkPolicy，性能更好，大规模集群推荐
- [ ] **iptables vs ipvs（kube-proxy模式）**：
  - iptables：规则链逐条匹配，Service数量多时性能差（O(n)）
  - ipvs：基于hash表查找（O(1)），支持更多负载均衡算法（rr/lc/sh/dh等），大规模集群必须用ipvs
- [ ] **Nginx Ingress 原理**：Ingress Controller监听K8s API → 感知Ingress规则变化 → 生成Nginx配置 → reload Nginx → 实现域名/路径路由
- [ ] **CNI/CSI/CRI**：
  - CNI（Container Network Interface）：容器网络接口标准（Flannel/Calico）
  - CSI（Container Storage Interface）：容器存储接口标准（Ceph/云盘）
  - CRI（Container Runtime Interface）：容器运行时接口标准（containerd/Docker）

#### 2.5 高频 kubectl 命令（必须熟练）
```bash
# ===== 查看资源 =====
kubectl get pods -o wide                    # 查看Pod在哪个Node、IP多少
kubectl get svc / deploy / nodes / ns
kubectl get all -n <namespace>              # 查看命名空间下所有资源
kubectl describe pod <pod_name>             # 查看Pod详情和Events（排错第一步！）
kubectl logs <pod_name>                     # 查看容器日志
kubectl logs -f <pod_name> --tail=100      # 实时跟踪最后100行
kubectl logs <pod_name> -c <container_name> # 多容器Pod指定容器
kubectl exec -it <pod_name> -- /bin/bash    # 进入Pod交互

# ===== 操作 =====
kubectl scale deploy/nginx --replicas=5     # 手动扩缩容
kubectl rollout status deploy/nginx          # 查看滚动更新状态
kubectl rollout history deploy/nginx         # 查看发布历史
kubectl rollout undo deploy/nginx            # 回滚到上一版本
kubectl rollout undo deploy/nginx --to-revision=2  # 回滚到指定版本
kubectl apply -f app.yaml                    # 应用配置（声明式）
kubectl delete -f app.yaml

# ===== 节点维护 =====
kubectl cordon <node>                        # 标记节点不可调度（新Pod不会调度上来）

# ===== 排错 =====
kubectl get events --sort-by=.metadata.creationTimestamp  # 按时间排序查看事件
kubectl top nodes                              # 查看节点资源使用（需metrics-server）

```

#### 2.6 其他高频问题
- [ ] **etcd 备份恢复**：
  - 备份：`etcdctl snapshot save backup.db --endpoints=... --cacert=... --cert=... --key=...`
  - 恢复：`etcdctl snapshot restore backup.db --data-dir=/var/lib/etcd`
- [ ] **RBAC 权限控制**：
  - Role（命名空间级权限）vs ClusterRole（集群级权限）
  - RoleBinding（命名空间内绑定）vs ClusterRoleBinding（集群范围绑定）
- [ ] **Pod 创建完整流程**：
  kubectl提交 → apiserver认证鉴权写入etcd → scheduler调度到Node → kubelet收到 → 调用CRI拉镜像启动容器 → 探针检测通过 → 加入Endpoints → Service可访问
- [ ] **K8s 故障排查思路**：
  Pod起不来？→ `kubectl describe pod` 看Events → 常见原因：镜像拉取失败(ImagePullBackOff)、资源不足(Pending)、探针失败(CrashLoopBackOff)、PVC绑定失败、调度失败(0/3 nodes available)
- [ ] **ConfigMap 热更新**：更新ConfigMap后，挂载的Pod不会自动更新，需要滚动重启Pod（或使用reloader等工具）
- [ ] **Pod 无法被删除**：可能有finalizer，`kubectl edit pod <name>` 删除finalizers字段

### 模块 3：Docker 容器技术 ⭐⭐⭐（90% JD要求）

**JD 原文摘录：**
- "熟练使用 Docker/containerd 等容器运行时"（腾讯）
- "精通 Kubernetes/Docker 容器化部署、配置、故障处理"（51job-K8s运维）

**必背面试题：**

#### 3.1 核心原理
- [ ] **Docker vs 虚拟机**：VM是硬件级虚拟化（有完整Guest OS，镜像几GB，启动分钟级）；Docker是进程级虚拟化（共享Host内核，镜像MB级，启动秒级）
- [ ] **三大核心技术**：
  - **Namespace**：资源隔离（PID进程隔离、NET网络隔离、IPC进程间通信、MNT文件系统、UTS主机名、USER用户）
  - **Cgroups**：资源限制（CPU、内存、IO、进程数）
  - **UnionFS（联合文件系统）**：分层镜像，层叠挂载，写时复制(CoW)
- [ ] **三大概念**：镜像(Image，只读模板)、容器(Container，镜像运行实例)、仓库(Registry，镜像存储分发)
- [ ] **容器运行时演进**：Docker → containerd（K8s 1.24+ 移除dockershim，默认containerd）→ CRI-O

#### 3.2 Dockerfile 高频考点
- [ ] **CMD vs ENTRYPOINT**：
  - CMD：容器启动默认命令，可被`docker run`末尾参数覆盖
  - ENTRYPOINT：容器启动入口命令，不会被覆盖（`--entrypoint`可改）
  - 配合使用：ENTRYPOINT定固定命令，CMD传默认参数
- [ ] **COPY vs ADD**：
  - 两者都能复制本地文件到镜像
  - ADD额外支持：从URL下载文件、自动解压本地tar包
  - **推荐用COPY**，更透明可控
- [ ] **减小镜像体积的方法**：
  - 选小基础镜像（alpine ~5MB / distroless / debian-slim）
  - **多阶段构建**（multi-stage build）：编译阶段用大镜像，运行阶段只拷贝产物
  - 清理包管理缓存：`yum clean all` / `apt-get clean && rm -rf /var/lib/apt/lists/*`
  - 合并RUN指令减少层数
  - 用`.dockerignore`排除不需要的文件
- [ ] **常用指令**：FROM / WORKDIR / COPY / ADD / RUN / CMD / ENTRYPOINT / EXPOSE / ENV / ARG / VOLUME / USER / HEALTHCHECK

#### 3.3 Docker 网络
- [ ] **四种网络模式**：
  - `bridge`（默认）：容器连接到docker0网桥，通过NAT访问外网
  - `host`：共享Host网络命名空间，无隔离，性能最好（端口直接占用Host端口）
  - `none`：无网络，只有lo回环
  - `container`：共享另一个容器的网络命名空间（K8s Pod内多容器就是这种模式）
- [ ] **容器间通信**：同一自定义bridge网络可通过容器名互访（DNS自动解析）；默认bridge网络只能用IP

#### 3.4 数据持久化
- [ ] **Volume（数据卷）**：Docker管理，`/var/lib/docker/volumes/`，推荐方式

- "熟悉 Nginx/Apache 与 PHP-FPM 的配置与调优"（51job-云运维）

**必背面试题：**

#### 5.1 TCP/IP
- [ ] **OSI七层 vs TCP/IP四层**：
  - OSI：物理层→数据链路层→网络层→传输层→会话层→表示层→应用层
  - TCP/IP：网络接口层→网际层(IP)→传输层(TCP/UDP)→应用层(HTTP/DNS等)
- [ ] **TCP 三次握手**：
  - 客户端发 SYN（seq=x）→ 服务端回 SYN+ACK（seq=y, ack=x+1）→ 客户端发 ACK（ack=y+1）
  - 为什么三次？—— 防止已失效的连接请求突然到达服务端造成资源浪费；同步双方序列号
- [ ] **TCP 四次挥手**：
  - 主动方发 FIN → 被动方回 ACK（此时被动方可能还有数据要发）→ 被动方发 FIN → 主动方回 ACK
  - 为什么四次？—— TCP全双工，两个方向要独立关闭；被动方收到FIN后可能还有数据没发完，不能立即FIN
- [ ] **TIME_WAIT 状态**：主动关闭方最后进入TIME_WAIT，等待2MSL确保最后一个ACK到达。过多怎么办？—— 调`net.ipv4.tcp_tw_reuse=1`、`tcp_fin_timeout`缩短、应用层用连接池
- [ ] **TCP vs UDP**：
  - TCP：面向连接、可靠传输（确认重传、序号、流量控制、拥塞控制）、字节流、头部20字节
  - UDP：无连接、不可靠、数据报、头部8字节、快（DNS/视频/游戏用UDP）
- [ ] **ping 用什么协议**：ICMP（Internet控制报文协议），网络层

#### 5.2 HTTP / HTTPS
- [ ] **常见状态码及排查方向**：
  - 200 成功 / 301 永久重定向 / 302 临时重定向 / 304 未修改(缓存)
  - 400 请求参数错误 / 401 未认证 / 403 禁止访问 / 404 资源不存在
  - **413** 请求体太大 → 调Nginx `client_max_body_size`
  - **499** 客户端主动断开（Nginx特有）→ 接口太慢/用户取消/网络差
  - **500** 服务端内部错误 → 查应用日志
  - **502** Bad Gateway → 后端服务挂了/端口不通/代理配置错误
  - **503** Service Unavailable → 后端过载/维护/限流
  - **504** Gateway Timeout → 后端响应超时
- [ ] **HTTP vs HTTPS**：HTTPS = HTTP + SSL/TLS加密，默认443端口，需要证书
- [ ] **TLS 握手过程**（了解）：Client Hello → Server Hello+证书 → 客户端验证证书+密钥交换 → 加密通信

#### 5.3 Nginx（几乎必考）
- [ ] **Nginx 为什么快**：epoll事件驱动模型（异步非阻塞IO）+  master/worker多进程架构
- [ ] **负载均衡算法**：
  - `round_robin`（轮询，默认）
  - `weight`（加权轮询，按权重分配）
  - `ip_hash`（按客户端IP哈希，会话保持，同一用户始终到同一后端）
  - `least_conn`（最少连接数，适合长连接场景，避免某台后端连接堆积）
  - `fair`（按响应时间，第三方模块）
  - `url_hash`（按URL哈希，缓存场景，第三方模块）
- [ ] **四层 vs 七层负载均衡**：
  - 四层：基于IP+端口转发（LVS、Nginx stream模块），看不到HTTP内容
  - 七层：基于URL/Header/Cookie等应用层信息（Nginx、HAProxy），可做内容路由
- [ ] **反向代理核心配置**：
  ```nginx
  location / {
      proxy_pass http://backend;
      proxy_set_header Host $http_host;
      proxy_set_header X-Real-IP $remote_addr;           # 传递真实客户端IP
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      proxy_connect_timeout 30s;
      proxy_read_timeout 60s;
  }
  ```
- [ ] **Nginx 常用优化参数**：
  - `worker_processes auto`（CPU核数）
  - `worker_connections 65535`（单进程最大连接数）
  - `keepalive_timeout 65`（长连接超时）
  - `client_max_body_size 20m`（上传文件大小限制）
  - `gzip on`（压缩）
  - `sendfile on` + `tcp_nopush on`（高效文件传输）
- [ ] **location 匹配优先级**：精确匹配`=` → 前缀匹配`^~` → 正则匹配`~`/`~*` → 普通前缀匹配 → `/`
- [ ] **Nginx 配置检查和重载**：`nginx -t`（语法检查）→ `nginx -s reload`（平滑重载，不中断服务）

#### 5.4 DNS / CDN
- [ ] **DNS 解析过程**：浏览器缓存 → 系统缓存(hosts) → 本地DNS服务器(递归查询) → 根DNS → 顶级域DNS(.com) → 权威DNS → 返回IP
- [ ] **CDN 原理**：用户请求 → DNS调度到最近边缘节点 → 边缘节点有缓存直接返回 → 无缓存回源站获取 → 缓存并返回
- [ ] **DNS 记录类型**：A(IPv4)、AAAA(IPv6)、CNAME(别名)、MX(邮件)、TXT(文本)、NS(域名服务器)

### 模块 7：数据库 MySQL ⭐⭐（70% JD要求）

**JD 原文摘录：**
- "熟悉 MySQL / MariaDB 运维：主从复制、读写分离、慢查询分析、备份与时间点恢复"（51job-云运维）
- "熟悉主流数据库和中间件的运维管理，包括 MySQL、Redis、Kafka、RocketMQ、Elasticsearch 等，具备高可用、备份恢复、性能调优和故障处理经验"（猎聘）

**必背面试题：**

#### 7.1 基础
- [ ] **MySQL 存储引擎**：
  - InnoDB（默认）：支持事务、行级锁、外键、崩溃恢复，聚簇索引
  - MyISAM：不支持事务、表级锁、全文索引，速度快但不推荐
- [ ] **索引原理**：B+树结构，为什么快？——减少磁盘IO次数、有序范围查询；缺点：占用存储空间、写操作需维护索引
- [ ] **索引类型**：主键索引、唯一索引、普通索引、联合索引（最左前缀原则）、覆盖索引
- [ ] **MySQL 日志**：
  - **binlog**（二进制日志）：Server层，记录所有写操作的SQL语句，用于主从复制和数据恢复
  - **redo log**（重做日志）：InnoDB层，物理日志，记录页的修改，保证事务持久性（WAL预写式日志）
  - **undo log**（回滚日志）：InnoDB层，逻辑日志，记录数据修改前的版本，用于事务回滚和MVCC
  - **slow log**（慢查询日志）：记录执行时间超过long_query_time的SQL，用于性能优化
- [ ] **binlog 三种格式**：
  - STATEMENT：记录SQL语句，日志小但可能主从不一致（如now()、uuid()）
  - ROW：记录行数据变化，安全但日志大（推荐，MySQL 8.0默认）
  - MIXED：混合模式，自动选择

#### 7.2 主从复制（必考）
- [ ] **主从复制原理**：
  1. Master将写操作记录到binlog
  2. Slave的IO线程连接Master，拉取binlog写入relay log（中继日志）
  3. Slave的SQL线程读取relay log，重放到从库
- [ ] **复制模式**：
  - 异步复制（默认）：Master写完binlog即返回，不等待Slave，性能好但可能丢数据
  - 半同步复制：至少一个Slave确认收到relay log才返回，兼顾性能和数据安全
  - 全同步：所有Slave都确认才返回，最安全但性能差
- [ ] **GTID**：全局事务ID，每个事务唯一标识，简化主从切换和故障恢复
- [ ] **主从延迟排查**：
  - `Seconds_Behind_Master`（不太准确，参考用）
  - 原因：大事务、从库性能差、网络延迟、从库有慢查询阻塞SQL线程
  - 解决：优化大事务、从库升级硬件、开启并行复制
- [ ] **主从中断恢复**：
  - 查看错误：`show slave status\G` 看 Last_Error
  - 跳过错误：`stop slave; set global sql_slave_skip_counter=1; start slave;`（谨慎）
  - 严重时重新搭建从库

#### 7.3 备份恢复
- [ ] **备份方式**：
  - 逻辑备份：`mysqldump --single-transaction --all-databases > backup.sql`（一致性备份，适合小库）
  - 物理备份：XtraBackup（Percona出品，在线热备，适合大库，不锁表）
- [ ] **备份策略**：全量备份（每天/每周）+ 增量备份（binlog实时）
- [ ] **恢复**：
  - 全量恢复：`mysql < backup.sql`
  - 时间点恢复(PITR)：全量备份 + binlog回放（`mysqlbinlog --start-datetime=... binlog.* | mysql`）
- [ ] **RTO/RPO**（51job JD提到）：
  - RTO（恢复时间目标）：故障后多久能恢复服务
  - RPO（恢复点目标）：最多能容忍丢失多少数据

#### 7.4 性能优化
- [ ] **慢查询分析**：开启slow_query_log → 用mysqldumpslow或pt-query-digest分析 → EXPLAIN看执行计划 → 加索引/优化SQL
- [ ] **EXPLAIN 关键字段**：type（访问类型，const>ref>range>index>ALL）、key（实际用的索引）、rows（扫描行数）、Extra（Using filesort/Using temporary需优化）
- [ ] **常见优化**：避免SELECT *、避免在索引列上用函数/运算、小表驱动大表、LIMIT分页优化、分库分表（大数据量）

### 模块 9：中间件 ⭐⭐（60% JD要求）

**JD 原文摘录：**
- "熟悉 Nginx、Redis、Mysql、kafka、Rabbitmq、zookeeper、minio 组件的容器化部署、使用、调优"（51job-K8s运维）
- "负责数据库、中间件及基础组件的运维保障，包括 MySQL、Redis、Kafka、RocketMQ、Elasticsearch、配置中心、注册中心、网关等组件"（猎聘）

**必背：**

#### 9.1 Redis
- [ ] **五种数据结构**：String（字符串/计数器/缓存）、Hash（对象/字段）、List（列表/队列）、Set（集合/去重）、ZSet（有序集合/排行榜）
- [ ] **持久化**：
  - RDB（快照）：定时fork子进程dump内存到磁盘，恢复快但可能丢数据
  - AOF（追加日志）：每条写命令追加到文件，数据安全但文件大、恢复慢
  - 混合持久化（Redis 4.0+）：RDB + AOF增量，兼顾速度和安全
- [ ] **高可用**：主从复制 → 哨兵(Sentinel，自动故障转移) → Cluster（分片集群，数据分片存储，水平扩展）
- [ ] **缓存三大问题**：
  - **缓存穿透**：查询不存在的数据，缓存不命中直接打DB → 解决：布隆过滤器、缓存空值
  - **缓存击穿**：热点key过期瞬间大量请求打DB → 解决：互斥锁、热点key永不过期
  - **缓存雪崩**：大量key同时过期或Redis宕机 → 解决：过期时间加随机值、多级缓存、Redis高可用
- [ ] **内存淘汰策略**：noeviction（默认，不淘汰报错）、allkeys-lru（所有key LRU）、volatile-lru（过期key LRU）、allkeys-lfu、volatile-lfu、allkeys-random、volatile-random、volatile-ttl

#### 9.2 Kafka
- [ ] **核心概念**：Broker（Kafka服务器节点）、Topic（主题，消息分类）、Partition（分区，Topic的分片，并行度单位）、Producer（生产者）、Consumer（消费者）、Consumer Group（消费者组，组内负载均衡，组间广播）、Offset（消息偏移量）、Replica（副本，Leader/Follower）
- [ ] **为什么快**：顺序写磁盘（页缓存）、零拷贝(sendfile)、批量发送、数据压缩
- [ ] **消息可靠性**：生产者acks=all（所有ISR副本确认）、副本数≥3、min.insync.replicas≥2、消费者手动提交offset
- [ ] **消息顺序性**：同一Partition内有序，全局有序需单Partition（牺牲并行度）

#### 9.3 Elasticsearch
- [ ] **核心概念**：Index（索引，类似数据库）、Document（文档，类似行）、Shard（分片，水平扩展）、Replica（副本，高可用）、倒排索引（分词→文档映射，全文检索核心）
- [ ] **ELK中的角色**：存储和搜索引擎，日志数据的存储和查询

### 模块 10：安全运维 & 高可用 & 其他高频要求

#### 10.1 安全运维（40% JD要求，越来越受重视）
- [ ] **WAF（Web应用防火墙）**：防护SQL注入、XSS、CC攻击等Web攻击
- [ ] **DDoS防护**：流量清洗，抗大流量攻击
- [ ] **堡垒机**：统一运维入口，操作审计，权限管控
- [ ] **最小权限原则**：账号只给必要权限，定期审计
- [ ] **MFA/2FA**：多因素认证，强制开启
- [ ] **密钥/证书管理**：定期轮换，不硬编码在代码里
- [ ] **安全基线**：TLS配置、CSP、关闭不必要端口和服务、漏洞扫描修复闭环
- [ ] **K8s安全**：RBAC权限控制、NetworkPolicy网络策略、镜像安全扫描(Trivy)、Pod Security Standards、Seccomp/AppArmor

#### 10.2 高可用架构
- [ ] **Keepalived + Nginx**：VRRP协议实现VIP漂移，主备自动切换
- [ ] **LVS 三种模式**：
  - DR（直接路由）：性能最高，请求经LVS，响应直接回客户端（不经过LVS），要求RS和VIP同网段
  - NAT：进出都经过LVS，LVS做DNAT+SNAT，RS网关指向LVS
  - TUN（隧道）：IP隧道封装，跨网段，RS需支持隧道协议
- [ ] **LVS vs Nginx vs HAProxy**：
  - LVS：四层，性能最高（百万级QPS），但不支持七层
  - Nginx：七层，灵活，支持HTTP/HTTPS/邮件，性能万级QPS
  - HAProxy：七层，专业负载均衡，支持TCP和HTTP，性能比Nginx略高

#### 10.3 故障排查方法论（90% JD要求"故障排查能力"）
- [ ] **排查思路**：
  1. 确认现象和影响范围（哪些用户/服务/功能受影响）
  2. 分层排查：网络层(DNS/连通性) → 系统层(CPU/内存/磁盘/连接数) → 应用层(日志/错误) → 数据层(慢查询/锁/连接池)
  3. 查看监控和日志（时间点对齐）
  4. 快速止血（重启/扩容/切流量/降级），优先恢复服务
  5. 根因分析(RCA)，输出复盘报告
- [ ] **MTTD/MTTR**（51job JD提到）：
  - MTTD（平均检测时间）：故障发生到被发现的时间
  - MTTR（平均恢复时间）：故障发生到恢复服务的时间
- [ ] **RCA复盘报告**（多个JD要求"24-48小时内输出"）：根因、影响面、时间线、改进项、负责人、截止时间

#### 10.4 SLO/SLI/SLA（腾讯/上海AI实验室JD提到）
- [ ] **SLI（服务等级指标）**：可量化的指标（可用性、延迟、错误率）
- [ ] **SLO（服务等级目标）**：SLI的目标值（如99.9%可用性、P99延迟<200ms）
- [ ] **SLA（服务等级协议）**：与客户的正式协议，SLO未达成有赔偿

#### 10.5 软实力要求（多个JD明确提到）
- [ ] **文档撰写能力**：架构拓扑、部署手册、故障处置手册、巡检清单、变更SOP、Runbook
- [ ] **跨团队沟通**：与研发、安全、测试、产品协同推进
- [ ] **on-call/7×24值班**：几乎所有运维岗都要求，需能接受
- [ ] **抗压能力**：线上故障时能冷静处理
- [ ] **责任心和自驱力**：主动发现和解决问题

## 六、面试中高频被问到的场景题（准备好STAR回答）

1. **"线上服务突然不可用，你怎么排查？"** —— 准备好分层排查思路和具体命令
