# Redis 知识体系全景总结

## 一、基本概念与定位

**Redis**（Remote Dictionary Server）是一个开源的、基于内存的高性能键值存储系统，常被用作**数据库、缓存、消息代理**。它通过键值对（Key-Value）方式存储数据，支持丰富的数据结构，所有数据主要存储在内存中，因此读写速度极快（可达 10万次/秒）。

与 Memcached 相比，Redis 的优势在于：
- **支持数据持久化**（RDB/AOF）
- **数据结构更丰富**（不仅仅是 String）
- **提供高级功能**（事务、发布/订阅、Lua 脚本等）

---

## 二、核心特性

### 2.1 速度极致：万级读写的底层支撑
- **全内存存储**：内存访问延迟仅纳秒级，远优于磁盘 I/O（毫秒级）。
- **单线程模型**：Redis 6.0 之前完全单线程，避免了线程切换和锁竞争；6.0 后引入多线程处理网络 I/O，但命令执行仍保持单线程，保证原子性。
- **C 语言实现**：贴近操作系统，执行效率极高。

### 2.2 数据结构丰富：不止于键值对

| 结构       | 说明                             | 适用场景                             |
| ---------- | -------------------------------- | ------------------------------------ |
| **String** | 文本、数字、二进制（最大 512MB） | 共享 session、分布式锁、计数器、限流 |
| **Hash**   | 适合存储对象，支持字段级操作     | 缓存用户信息、商品详情               |
| **List**   | 有序可重复，支持栈/队列操作      | 消息队列、最新评论、时间轴           |
| **Set**    | 无序不可重复，支持集合运算       | 标签系统、好友关系、共同关注         |
| **ZSet**   | 按分数排序，支持范围查询         | 游戏排行榜、热门商品、优先级队列     |

此外，Redis 还支持 **Bitmaps**（位图）、**HyperLogLog**（基数统计）、**GEO**（地理定位）等扩展结构。

### 2.3 功能全面：满足复杂场景需求
- **持久化**：RDB 快照 + AOF 日志，防止内存数据丢失。
- **主从复制**：实现读写分离，分担读压力。
- **高可用**：哨兵模式（Sentinel）自动故障转移。
- **分布式**：集群模式（Cluster）支持水平扩容，最多 16384 个槽位。
- **附加功能**：键过期、发布订阅、Lua 脚本、事务、流水线（Pipeline）等。

## 三、持久化机制与磁盘选型

### 3.1 RDB 持久化
- 在指定时间间隔生成数据集的时间点快照。
- **优点**：文件紧凑，恢复速度快。
- **缺点**：可能丢失最后一次快照后的数据。

### 3.2 AOF 持久化
- 记录所有写操作命令，重启时重放命令恢复数据。
- **优点**：数据丢失少（可配置每秒同步或每次写同步）。
- **缺点**：文件体积大，恢复速度较慢。

**最佳实践**：通常同时开启 RDB 和 AOF，重启时优先使用 AOF 保证数据完整性。

### 3.3 磁盘选型：SSD 是标配
- **机械硬盘（HDD）**：随机 I/O 性能差（寻道时间数毫秒），持久化时易导致主线程阻塞、服务卡顿，**不推荐生产环境使用**。
- **固态硬盘（SSD）**：随机读写延迟低（微秒级），IOPS 高，能保证 AOF fsync 快速完成，避免主线程阻塞。
- **建议**：为 Redis 数据目录（RDB/AOF 文件）单独配备高性能 SSD，并与系统盘隔离。

## 四、内存规划与 fork() 机制

### 4.1 内存规划原则
- **数据量估算**：计算基准数据量（如 10GB）。
- **预留余量**：
  - 内部开销 + 内存碎片：额外预留 **20%**。
  - 操作系统预留：`maxmemory` 建议设为物理内存的 **70%~80%**。
  - 持久化场景（AOF 重写/RDB 快照）可能需要额外内存（写时复制），建议总内存为数据集的 **1.5~2 倍**。
- **分片策略**：单实例内存不宜过大（建议 ≤ 64GB），避免持久化时 fork 耗时过长、故障恢复慢。使用 Redis Cluster 将数据分散到多个节点。

### 4.2 fork() 系统调用
- Redis 在生成 RDB 或 AOF 重写时会调用 `fork()` 创建子进程，子进程负责持久化，父进程继续处理请求。
- **写时复制**：子进程刚创建时与父进程共享内存页，只有当父进程修改某页数据时，内核才复制该页，从而降低 fork 开销。
- **影响**：若实例较大且写入频繁，写时复制可能导致内存占用突增，需确保有足够空闲内存。

## 五、部署模式与高可用

| 模式         | 说明                                                         | 适用场景             |
| ------------ | ------------------------------------------------------------ | -------------------- |
| **单实例**   | 一个主节点，可搭配从节点实现读写分离，但主故障不会自动切换。 | 开发测试、小型应用   |
| **哨兵模式** | 监控主节点，自动故障转移，实现高可用。                       | 生产环境需要自动容错 |
| **集群模式** | 多主多从，数据分片（16384 槽位），支持水平扩展。             | 海量数据、高并发写入 |

### 5.1 实际部署中的服务器规划
- **生产环境强烈建议将 Redis 与关系型数据库（如 MySQL）分离**，避免资源争抢（内存、磁盘 I/O、CPU），实现故障隔离和独立扩缩容。
- **开发/测试环境**可共存以节省资源。

## 六、典型应用场景

### 6.1 缓存加速
- **模式**：Cache-Aside（旁路缓存）
  - 读请求先查 Redis，命中则返回；未命中则查数据库，再写入 Redis 并设置过期时间。
- **实践**：Value 大小控制在 10KB 以内，使用 Pipeline 批量读取，TTL 采用随机过期防止雪崩。

### 6.2 分布式锁
- 使用 `SET key random_value NX PX` 命令实现原子性加锁。
- Redlock 算法：向多个独立节点请求锁，多数成功则视为获取锁。

### 6.3 排行榜
- 使用 ZSet 存储用户分数，`ZADD` 添加/更新，`ZRANGE` 获取排名。

### 6.4 消息队列
- 使用 List 的 `LPUSH`/`RPOP` 或 Stream 结构实现简单的消息队列。
- 也可用 ZSet 按时间戳排序实现延迟队列。

## 七、在代码中操作 Redis

### 7.1 客户端连接五步骤（以 Node.js 为例）
1. **引入客户端库**：`import { createClient } from 'redis';`
2. **建立连接**：`const client = createClient({ url: 'redis://host:6379' });`
3. **执行命令**：`await client.set('key', 'value');`
4. **处理结果**：`const val = await client.get('key');`
5. **关闭连接**：`client.quit();` 或 `client.disconnect();`

### 7.2 数据结构转换：数据库 → Redis
数据库中的表行数据通常映射为 Redis 的 **Hash** 或 **JSON 序列化后的 String**。例如：
```sql
-- MySQL 表 user
id | name | age
1  | Alice| 30
```
```redis
# 映射为 Hash
HSET user:1 name "Alice" age 30

# 或映射为 JSON String
SET user:1 '{"id":1,"name":"Alice","age":30}'
```

## 八、优缺点分析

### ✅ 优点
- **性能极高**：内存操作，10万+ QPS
- **数据结构丰富**：灵活应对多种业务
- **持久化支持**：数据可落地
- **高可用与分布式**：哨兵、集群
- **功能全面**：过期、Lua、Pub/Sub 等

### ❌ 缺点
- **内存受限**：数据量受物理内存限制，成本高
- **单线程模型**：虽高效，但单个耗时命令（如 `KEYS *`）会阻塞
- **不支持复杂查询**：无 SQL 关联查询
- **事务不支持回滚**：仅保证原子性，出错需应用层处理
- **数据一致性问题**：内存数据宕机可能丢失，依赖持久化

## 九、Redis vs Memcached

| 特性     | Redis                                    | Memcached  |
| -------- | ---------------------------------------- | ---------- |
| 数据结构 | 丰富（String、Hash、List、Set、ZSet 等） | 仅 String  |
| 持久化   | 支持（RDB/AOF）                          | 不支持     |
| 分布式   | 原生集群                                 | 客户端分片 |
| 事务     | 支持（Lua 脚本）                         | 不支持     |
| 大对象   | 支持 >1MB                                | 限制 1MB   |
| 高可用   | 哨兵、集群                               | 无         |

## 十、最佳实践与常见问题

### 10.1 Key 设计
- 采用命名空间，如 `product:{id}:detail`
- 避免过长 Key（占用内存），但也要有可读性

### 10.2 Value 大小
- 控制在 **10KB 以内**，避免网络传输和内存浪费
- 大对象可考虑压缩后存储，或拆分到多个 Key

### 10.3 热点 Key 处理
- 使用 `redis-cli --hotkeys` 识别热点
- 热点 Key 可本地缓存（如多级缓存）或打散（增加随机后缀）

### 10.4 数据一致性
- 更新数据库后，删除缓存（下次读取时重建）或更新缓存
- 使用 Lua 脚本保证多个操作的原子性

### 10.5 持久化调优
- 避免在业务高峰期触发 RDB/AOF 重写，可手动定时或调低阈值
- 监控 `aof_delayed_fsync` 指标，判断磁盘是否成为瓶颈

### 10.6 内存监控
- 观察 `used_memory`、`mem_fragmentation_ratio`（内存碎片率）
- 碎片率 >1.5 可考虑重启或启用自动内存整理（`activedefrag yes`）

## 十一、总结

Redis 凭借其**极致的性能、丰富的数据结构、灵活的高可用方案**，已成为现代互联网架构中不可或缺的组件。它适用于**缓存加速、分布式锁、排行榜、消息队列**等场景，但受限于内存成本和单线程模型，不适合存储海量数据或需要复杂查询的业务。

在实际应用中，需根据业务特点合理规划内存、选型磁盘、设计数据结构，并结合数据库、消息队列等组件构建健壮的系统。掌握 Redis 的核心原理与最佳实践，能帮助你在高并发、低延迟的场景下游刃有余。
