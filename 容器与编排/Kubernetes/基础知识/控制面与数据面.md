# 控制面与数据面

> ⭐ 这是整个 K8s 的地基概念。不懂这个，Service / Ingress / NetworkPolicy / CNI 全都听不懂。
> 相关：[[Service完全打通-调谐循环视角]]

---

## 一、一句话定义

- **控制面（Control Plane）**：做决定、写表、下指令。**低频**，不碰数据包。
- **数据面（Data Plane）**：按表执行、转发数据。**高频**，每个包都走，自己不思考。

---

## 二、用你最熟的东西打比方：路由器

一台路由器里天生就住着两套东西：

| | 控制面 | 数据面 |
|---|---|---|
| **是谁** | CPU 跑 OSPF/BGP 协议算路由 | 线卡 ASIC 查表转发 |
| **干什么** | 决定"去 10.0.0.0/8 走哪个口" | 照着表把包扔出去 |
| **频率** | 几分钟一次（拓扑变化才重算） | 每秒百万次（每个包都查） |
| **用啥硬件** | 通用 CPU | 专用芯片 |
| **挂了会怎样** | 路由不再更新，**现有转发照常** | **立刻断网** |

这个类比可以**逐格平移到 K8s**：

| 路由器 | K8s Service |
|--------|-------------|
| CPU 跑 OSPF 算路由 | EndpointSlice 控制器算 Pod 名单 |
| 路由表 FIB | iptables / IPVS 规则 |
| ASIC 线卡查表转发 | 内核 netfilter 查规则转发 |

---

## 三、终身可用的判断标准

> **问一句：这玩意每秒被调用多少次？**

| 频率 | 归属 |
|------|------|
| 几分钟一次、几秒一次 | 控制面 |
| 每秒几千几万次、每个包都走 | **数据面** |

拿这把尺子量 Service 体系：
- EndpointSlice 控制器算名单 → Pod 变了才算一次 → **控制面**
- kube-proxy 写规则 → 名单变了才写 → **控制面**
- 内核 netfilter 转发 → **每个包都查** → **数据面**

---

## 四、K8s 组件归属表

| 组件 | 归属 | 频率 | 备注 |
|------|------|------|------|
| etcd | 控制面 | 读写请求级 | 存期望状态 |
| kube-apiserver | 控制面 | 请求级 | 控制面的总线 |
| kube-controller-manager | 控制面 | 低频 | 一堆循环 |
| kube-scheduler | 控制面 | 低频 | 只改 nodeName 字段 |
| kubelet | 控制面 | 低频 | 管 Pod 生死，**不转发数据** |
| **kube-proxy** | **控制面** | 低频 | ⚠️ **它不转发任何数据包**，只负责写规则 |
| CoreDNS | 控制面 | 中频 | 解析查询，比控制面略高 |
| **iptables / IPVS / netfilter** | **数据面** | 每包 | 真正动手转发的 |
| **CNI 插件**（Calico/Cilium） | **两面都有** | — | 配网口是控制面，转发包是数据面 |
| **Ingress Controller** | **两面都有** | — | 生成配置是控制面，nginx 转发是数据面 |

### 最容易搞错的两条

1. **kube-proxy 是控制面，不是数据面。** 名字带 proxy 特别容易误导。它挂了数据包的转发还在继续（已有连接靠 conntrack 撑着），只是新变化不再生效。
2. **CNI 和 Ingress Controller 是双面组件。** 它们既有控制器（watch apiserver 生成配置），又有转发进程。

---

## 五、为什么这个划分对运维特别重要

因为**两面的故障现象完全不一样**，排障时第一件事就是判断是哪面挂了。

| | 控制面挂了 | 数据面挂了 |
|---|---|---|
| **现象** | 老流量正常，**新变化不生效** | **直接断流** |
| **典型场景** | kube-proxy 挂了：已有连接还能跑，但新扩的 Pod 加不进来 | netfilter 规则被误清、CNI 网桥挂了：立刻全断 |
| **危险度** | 慢性、隐蔽，**容易被忽略很久** | 急性、立刻暴露 |
| **排查信号** | `kubectl get` 一切正常，但行为不对 | curl 直接超时 |

> **排障口诀**：
> **"老的好使、新的不生效" → 控制面；"不管新旧全断" → 数据面。**

举例：
- Service 扩容后新 Pod 接不到流量，但老 Pod 正常 → 控制面问题（EndpointSlice 没更新 / kube-proxy 没写规则）
- 整个 Service 一下子全不通 → 数据面问题（规则没了 / CNI 挂了）

---

## 六、回到"为什么 Service 是第一次分家"

| 模块 | 产物 | 有没有数据面 |
|------|------|-------------|
| Pod | 容器进程 | 没有，K8s 只负责拉起它 |
| Deployment | Pod（**东西**） | 没有，创建完就静静待着 |
| ConfigMap | 文件/环境变量 | 没有 |
| **Service** | **转发规则（规矩）** | ✅ **有！每个包都执行** |

**核心区别一句话：**

> **Deployment 造的是「东西」，Service 造的是「规矩」。东西造完就静静待着，规矩是要被反复执行的。**

Service 是你在 K8s 里遇到的**第一个产物为"规则"而非"对象"的模块**，所以它是第一个需要同时理解两面的地方。这就是"第一次分家"的含义。

往后学 Ingress、NetworkPolicy，本质上都是这个模式的重复——而且它们的控制器还常常不在 K8s 本体里（Ingress Controller 要自己装，NetworkPolicy 靠 CNI 落地）。
