## 一、Pod 网络模型

**核心概念**：Pod 内所有容器共享同一个网络命名空间，由 pause/infra 容器持有。

- Pod 启动时 kubelet 先创建 pause 容器 → 建立网络命名空间
- 其他容器通过 `JoinNetworkNamespace` 加入，共享 IP、端口空间、网络接口
- 容器之间通过 `localhost` 通信
- **端口冲突规则**：同一个 Pod 内的两个容器不能监听相同端口（共享端口空间）

**与 Docker 的对比**：

| 对比维度 | Docker 默认 | Kubernetes Pod |
|---------|-------------|----------------|
| 网络命名空间 | 每个容器独立 | Pod 内所有容器共享 |
| 容器间通信 | 需通过 bridge/overlay 网络 | 直接 localhost |
| 端口空间 | 每个容器独立 | Pod 级别共享 |

## 二、Pod 生命周期：Phase 与 Conditions

### Phase（全局状态，同一时间只有一个）

| Phase | 含义 |
|-------|------|
| `Pending` | 已创建但容器未全部运行（调度中、拉镜像、init 中） |
| `Running` | 至少一个容器正在运行 |
| `Succeeded` | 所有容器正常退出且不会再重启 |
| `Failed` | 至少一个容器非零退出 |
| `Unknown` | Node 失联，无法获取状态 |

### Conditions（多个独立维度，每个为 true/false/unknown）

| Condition | true 表示 | 何时变为 true |
|-----------|----------|-------------|
| `PodScheduled` | 已分配到 Node | 调度器写入 binding 后即 true |
| `Initialized` | init 容器已完成 | 无 init 容器则创建即 true |
| `ContainersReady` | 主容器通过 readiness | readiness probe 通过 |
| `Ready` | Pod 可接收流量 | ContainersReady + readinessGates 共同决定 |

**关键区分**：
- `Phase: Running` ≠ `Ready: true`（Running 表示容器在跑，Ready 表示可接流量）
- `Pending` 在容器重启时**不会出现**（OOM 重启 Phase 保持 Running）
- `Unknown` 只在 Node 失联时出现

### 实际查看：Phase 和 Conditions 不是混合显示的

`kubectl get pods` 的 `STATUS` 列展示的是 **Phase**（但 kubectl 做了增强显示），而 **Conditions** 藏在 `describe` / `-o yaml` 里，两者出现在不同命令层级：

```
# 看 Phase（STATUS 列）
kubectl get pods
NAME                     READY   STATUS             RESTARTS   AGE
nginx-xxx                1/1     Running            0          10h
crash-pod                0/1     CrashLoopBackOff   3          2m
#                              ↑ Phase 实际是 Running，但 kubectl 用容器故障状态覆盖显示

# 看 Conditions（describe 里）
kubectl describe pod nginx-xxx
...
Status:           Running          ← Phase
Conditions:
  Type              Status
  Initialized       True
  Ready             True
  ContainersReady   True
  PodScheduled      True
```

| | Phase | Conditions |
|---|-------|-----------|
| 查看命令 | `kubectl get pods` 的 STATUS 列 | `kubectl describe pod` 或 `get pod -o yaml` |
| 含义 | Pod 生命周期阶段（粗粒度） | 各项就绪条件的细粒度状态 |
| 取值 | Pending / Running / Succeeded / Failed / Unknown | Initialized / Ready / ContainersReady / PodScheduled |
| 同时存在 | 只有一个 Phase | 多个 Condition 可以同时为 true/false |

**核心结论**：`get pods` 默认看到的是 Phase（经过 kubectl 增强处理），Conditions 是独立的诊断信息层，两者不在同一命令层级混合显示。

## 三、Probe（探针）

三种检查方式：

| 方式 | 机制 | 成功条件 |
|------|------|---------|
| **ExecAction** | 容器内执行命令 | exit code == 0 |
| **HTTPGet** | HTTP GET 请求 | 2xx / 3xx |
| **TCPSocket** | TCP 连接尝试 | 端口开放 |

三种探针类型：

| Probe | 失败后果 | 用途 |
|-------|---------|------|
| **liveness** | kubelet 重启容器 | 检测"是否活着"，死锁/死循环保底 |
| **readiness** | 从 Service 摘除流量 | 检测"能否接流量"，防止发给不可用 Pod |
| **startup** | kubelet 重启容器 | 保护慢启动应用，运行期间暂停 liveness/readiness |

**关键参数**：
- `initialDelaySeconds`：启动后等多久开始检查
- `periodSeconds`：检查间隔
- `failureThreshold`：连续多少次失败才认为失败（默认 3）
- `successThreshold`：连续多少次成功才认为成功（默认 1）

**时序示例**：
```
initialDelaySeconds: 5, periodSeconds: 10
t=0  容器启动
t=5  第一次检查
t=15 第二次检查
t=25 第三次检查
...每 10 秒一次
```

**常见陷阱**：应用启动需 30 秒，liveness 设 initialDelaySeconds=5 → 启动期 liveness 失败 → 重启 → CrashLoopBackOff。解决方案：使用 startup probe 或加大 initialDelaySeconds。

## 四、Init 容器 & Sidecar 容器

### Init 容器

- 定义在 `spec.initContainers`，在主容器之前**顺序执行**
- **成功后才启动下一个**（不能有 restartPolicy: Always，失败会自动重试）
- 执行完即退出，不长期运行
- 用途：等待依赖就绪、初始化数据、设置权限

```yaml
spec:
  initContainers:
  - name: check-db
    image: busybox
    command: ['sh', '-c', 'until nc -z db 3306; do sleep 1; done']
```

执行顺序由定义在 `initContainers` 数组中的索引决定：

```
Init 容器 A（5s）→ Init 容器 B（3s）→ 主容器启动
                     总耗时 8s
```

### Sidecar 容器（v1.29+ 稳定）

- 定义在 `initContainers` 中，但标记 `restartPolicy: Always`
- 与主容器**并行启动**（不等退出，只等 readiness 通过）
- 长期运行，随 Pod 生命周期
- 用途：日志收集、代理、服务网格边车

```yaml
spec:
  initContainers:
  - name: log-sidecar
    image: fluentbit
    restartPolicy: Always   # 标记为 sidecar
    readinessProbe: ...     # 主容器等这个通过才启动
```

## 五、QoS 等级与驱逐

### 三级 QoS

QoS 由 `spec.containers[].resources.requests` 和 `limits` 决定，以 Pod 内**最差**的容器为准：

| QoS 等级 | 条件 | 驱逐优先级 |
|---------|------|-----------|
| **Guaranteed** | **所有**容器 requests == limits（且都设了） | 最低（最后被杀） |
| **Burstable** | 至少一容器有 requests，且不是全部满足 Guaranteed | 中等 |
| **BestEffort** | **所有**容器都没设 requests 和 limits | 最高（最先被杀） |

```yaml
# Guaranteed 示例
resources:
  requests: { cpu: 500m, memory: 512Mi }
  limits:   { cpu: 500m, memory: 512Mi }

# Burstable 示例
resources:
  requests: { cpu: 100m, memory: 256Mi }  # 有 requests
  limits:   { cpu: 200m, memory: 512Mi }  # requests < limits

# BestEffort 示例
# 什么都没设
```

**规则**：如果一个容器没设任何资源，整个 Pod 变为 BestEffort（哪怕其他容器设了 Guaranteed）。

### 驱逐（Eviction）

节点资源不足时 kubelet 的清理机制：

| 触发条件 | 驱逐对象 |
|---------|---------|
| 内存压力 | 按 QoS 等级（BestEffort → Burstable → Guaranteed） |
| 磁盘压力 | 按 ephemeral-storage 用量排名驱逐 |
| PID 压力 | 按 PID 用量驱逐 |

## 六、容器常见故障状态

| 状态（STATUS 列） | 本质原因 | 处理方向 |
|------------------|---------|---------|
| **CrashLoopBackOff** | 容器反复崩溃→重启→崩溃，kubelet 在退避 | 检查代码、日志、probe 配置 |
| **ImagePullBackOff** | 拉取镜像失败，退避重试 | 检查镜像名、私仓 Secret |
| **ErrImagePull** | 拉取镜像时出错 | 同上，网络问题 |
| **CreateContainerConfigError** | 引用了不存在的 ConfigMap/Secret | 检查引用名称 |
| **Init:Error** | Init 容器执行失败 | 检查 Init 命令 |
| **Init:CrashLoopBackOff** | Init 容器反复崩溃 | 修复 Init 容器 |
| **PodInitializing** | Init 完成，主容器启动中 | 短暂过渡状态，等 |
| **Pending** | 未被调度或还在准备 | 检查资源、挂载、镜像大小 |
| **Terminating** | 正在删除 | 等待/强制删除 |

## 七、纠正的误解

| # | 原误解 | 正确理解 | 状态 |

| 1 | "多容器 Pod 内每个容器有独立网络栈，可以监听相同端口" | Pod 共享网络命名空间，pause 容器建立基础网络设施，其他容器 join | ✅ **已解决** |
