## 一、间隔复习

### 1.1 Pod 启动顺序

**问题：下面 Pod 的容器启动顺序是什么？**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: review-pod
spec:
  initContainers:
  - name: init-1
    image: busybox
    command: ["sleep", "5"]
  - name: init-2
    image: busybox
    command: ["sleep", "3"]
  containers:
  - name: app
    image: nginx
  - name: sidecar
    image: fluentd
```

**答案**：

1. `init-1` 先启动，执行 `sleep 5`，等待完成
2. `init-2` 在 init-1 完成后启动，执行 `sleep 3`，等待完成
3. `app` 和 `sidecar` 在所有 init 容器完成后**同时**启动，它们之间没有先后顺序

**关键点**：
- init 容器是**串行**执行的：前一个完成后下一个才启动
- 普通容器（包括 YAML 里叫 `sidecar` 的）是**并行**启动的
- 注意：这个 YAML 里的 `sidecar` 只是个普通容器名字，不是 K8s 1.29+ 的 Sidecar 容器特性（那种是 `restartPolicy: Always` 的 init 容器）

---

### 1.2 Deployment 滚动更新

**问题**：`maxSurge=2` 和 `maxUnavailable=1` 分别控制什么？

**答案**：

- **maxSurge=2**：滚动更新时，最多允许比期望副本数多出 2 个 Pod。比如 `replicas=5`，更新过程中最多可以同时有 `5 + 2 = 7` 个 Pod 存在
- **maxUnavailable=1**：滚动更新时，最多允许 1 个 Pod 处于不可用状态

**具体场景（replicas=5）**：
- 正常服务中的 Pod 数量范围是：**4 到 7**
- 最小值 4：`replicas - maxUnavailable = 5 - 1 = 4`
- 最大值 7：`replicas + maxSurge = 5 + 2 = 7`

## 二、ConfigMap 详解

### 2.1 问题背景

你的应用需要连数据库。数据库地址在不同环境（开发、测试、生产）不一样。

**坏的做法**：
```go
// 代码里写死
dbHost := "prod-db.example.com"
```
→ 换环境要改代码、重编译、重新打包镜像。

**好的做法**：
```go
// 代码从环境变量读
dbHost := os.Getenv("DB_HOST")
```
→ 部署时传不同环境变量就行，代码不用改。

---

### 2.2 环境变量的基本用法

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  containers:
  - name: app
    image: my-app
    env:
    - name: DB_HOST
      value: "prod-db.example.com"
    - name: DB_PORT
      value: "5432"
    - name: ENV
      value: "production"
```

**工作原理**：Pod 创建时，K8s 在容器启动前设置好这些环境变量。容器里的进程通过 `os.Getenv("DB_HOST")` 就能读取。

---

### 2.3 ConfigMap 是什么

如果配置项很多（几十个），每个 Pod YAML 里重复写一堆 `env:` 就会：

1. **冗余**：多个 Deployment 共享同一套配置需要重复写
2. **难维护**：改一个配置要改多个 Pod 定义
3. **易出错**：某处忘记同步就会不一致

**ConfigMap 的解法**：把配置**抽出来**，变成一个独立的 K8s 对象。

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "prod-db.example.com"
  DB_PORT: "5432"
  ENV: "production"
```

Pod 引用它，不自己写死值：

```yaml
containers:
- name: app
  image: my-app
  envFrom:
  - configMapRef:
      name: app-config
```

`envFrom` 的作用：把 `app-config` 这个 ConfigMap 里**所有** key-value 都导入为容器的环境变量。

---

### 2.4 ConfigMap 的好处

1. **集中管理**：一个 ConfigMap 被多个 Pod 引用，改一处全部生效
2. **环境隔离**：开发/测试/生产各一套 ConfigMap，Pod 模板一样
3. **配置与镜像解耦**：改配置不需要重新构建镜像

**示例**：
```yaml
# 开发环境
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: dev
data:
  DB_HOST: "dev-db.example.com"
---
# 生产环境
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
  namespace: prod
data:
  DB_HOST: "prod-db.example.com"
```

Pod YAML 完全一样，只通过 namespace 区分环境。

---

### 2.5 Volume 挂载方式

除了环境变量，ConfigMap 还可以通过 **volume 挂载** 注入为文件。

```yaml
apiVersion: v1
kind: Pod
spec:
  volumes:                              # 第一步：声明一块存储空间
  - name: config
    configMap:
      name: app-config
  containers:
  - name: app
    image: my-app
    volumeMounts:                       # 第二步：挂载到容器路径
    - name: config
      mountPath: /etc/config
```

**理解方式**：

可以把 ConfigMap 想象成一个 USB 硬盘。
- `volumes`：声明"我有一个叫 `config` 的 USB 硬盘，里面装的是 `app-config` 的数据"
- `volumeMounts`：把这个硬盘"插"到容器的 `/etc/config` 目录
- `mountPath`：插入的路径

**容器里看到的结果**：

如果 ConfigMap 有两条数据：
```
DB_HOST=prod-db.example.com
DB_PORT=5432
```

容器里的文件系统会变成：
```
/etc/config/
├── DB_HOST    → 内容 "prod-db.example.com"
├── DB_PORT    → 内容 "5432"
```

每个 key 变成一个文件名，value 变成文件内容。

---

### 2.6 env vs volume 挂载的区别

| 方式 | 容器里看到的 | 更新 ConfigMap 后 Pod 生效？ |
|------|------------|---------------------------|
| env / envFrom | 环境变量 | ❌ 需要重启 Pod |
| volume 挂载 | 文件 | **文件系统会自动更新**（几分钟内） |

**"自动更新"并不意味着应用一定生效**。取决于应用如何读配置：

| 应用读取方式 | 是否生效 |
|------------|---------|
| 启动时一次性读取，缓存到内存 | ❌ 不生效，需重启 Pod |
| 每次请求都读取文件 | ✅ 自动生效 |
| 通过 inotify 监听文件变化 | ✅ 自动生效（热加载） |
| 定期重新读取（如每 30 秒） | ✅ 一段时间后生效 |

---

### 2.7 Volume 挂载的 symlink 更新机制

ConfigMap 挂载的文件更新不是直接替换文件，而是通过 **symlink 原子切换**：

```
/etc/config/DB_HOST
  → ..data/DB_HOST                          # 指向当前数据
  → ..2026_05_28_12_00_00/DB_HOST           # 旧版本的文件
  → ..2026_05_28_12_30_00/DB_HOST           # 新版本的文件
```

更新流程：

1. 你更新 ConfigMap：`kubectl edit configmap app-config`
2. kubelet 检测到变化，在节点上创建一个新的时间戳目录 `..2026_05_28_12_30_00/`
3. kubelet 把 `..data` 这个 symlink 原子性地指向新目录
4. 已经打开旧文件的进程：继续读旧 inode，**不中断**
5. 新打开文件的进程：通过 symlink 读到新目录，拿到**新内容**

这保证了服务在更新过程中不会中断。

## 三、Secret 详解

### 3.1 Secret 是什么

Secret 和 ConfigMap 几乎一样，区别是存**敏感数据**。

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  DB_PASSWORD: cHJvZC1zZWNyZXQ=    # base64 编码
```

引用方式完全一样：

```yaml
envFrom:
- secretRef:
    name: db-credentials
```

或者单独引用某个 key：

```yaml
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: DB_PASSWORD
```

---

### 3.2 为什么要有 ConfigMap 和 Secret 两个对象？

| | ConfigMap | Secret |
|---|---|---|
| 存储内容 | 非敏感配置 | 密码、token、SSH key、证书 |
| data 字段 | 明文 | **base64 编码** |
| stringData 字段 | ❌ 不支持 | ✅ 支持（明文自动编码） |
| 节点存储位置 | 普通文件系统 | **tmpfs（内存）** |
| etcd 存储 | 明文 | base64 编码 |
| 按需分发 | 分发到所有节点 | 只分发到需要它的节点 |
| RBAC 权限 | 所有用户可读 | 可配置细粒度访问控制 |

**核心设计理念**：API 的差异强迫开发者在设计时就区分"这是敏感数据"还是"这不是敏感数据"，避免密码被当作普通配置泄露。

---

### 3.3 Base64 是编码，不是加密

这是一个**非常重要的区分**：

```bash
# "prod-secret" 的 base64 编码
echo -n "prod-secret" | base64
# 输出: cHJvZC1zZWNyZXQ=

# 解码（一秒还原）
echo "cHJvZC1zZWNyZXQ=" | base64 -d
# 输出: prod-secret
```

| | 编码（Encoding） | 加密（Encryption） |
|---|---|---|
| 需要密钥？ | ❌ 不需要 | ✅ 需要 |
| 可逆性 | 公开可逆 | 只有有密钥才能解密 |
| 目的 | 数据格式转换 | 数据保密 |
| 例子 | Base64、Hex | AES、RSA |

**Secret 真正安全的机制**来自：
1. **tmpfs 存储**：挂载到节点时存在内存中，不落磁盘
2. **按需分发**：只在有 Pod 引用它的节点上才会出现
3. **etcd 加密**（可选）：开启 Encryption at Rest 后，在 etcd 中也是加密的
4. **RBAC 控制**：可以限制只有特定用户/ServiceAccount 才能读 Secret

---

### 3.4 data 与 stringData

**data 字段**（Secret 和 ConfigMap 都有）：

```yaml
data:
  KEY: base64编码后的值
```

**stringData 字段**（Secret 才有，ConfigMap 没有）：

```yaml
stringData:
  KEY: 明文值   # K8s 自动帮你转 base64 存入 data
```

`stringData` 是写 YAML 时的便利写法——不用手动 base64 编码，K8s 自动处理。

```yaml
# 这两种写法完全等价：
---
apiVersion: v1
kind: Secret
data:
  PASSWORD: cHJvZC1zZWNyZXQ=
---
apiVersion: v1
kind: Secret
stringData:
  PASSWORD: prod-secret
```

---

### 3.5 常用设计模式：ConfigMap + Secret 组合

一个应用通常同时需要非敏感和敏感配置：

```yaml
# 非敏感配置 → ConfigMap
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: "prod.example.com"
  DB_PORT: "5432"
  LOG_LEVEL: "info"
---
# 敏感配置 → Secret
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
stringData:
  DB_PASSWORD: "prod-secret"
  API_KEY: "sk-xxxxx"
```

Pod 同时引用两者：

```yaml
apiVersion: v1
kind: Pod
spec:
  containers:
  - name: app
    image: my-app
    envFrom:
    - configMapRef:
        name: app-config
    - secretRef:
        name: app-secret
```

这样容器里同时有四个环境变量：DB_HOST、DB_PORT、LOG_LEVEL、DB_PASSWORD、API_KEY。

## 四、核心概念速记

| 概念 | 是什么 | 用途 |
|------|--------|------|
| **ConfigMap** | K8s 对象 | 存非敏感配置 key-value |
| **Secret** | K8s 对象 | 存敏感数据，节点上存内存 |
| **data** | 字段 | ConfigMap/Secret 的数据内容 |
| **stringData** | 字段（Secret 独有） | 写明文，K8s 自动转 base64 |
| **env** | Pod 字段 | 设置单个环境变量 |
| **envFrom** | Pod 字段 | 把 ConfigMap/Secret 全部导入为环境变量 |
| **volumes** | Pod 字段（Pod 级别） | 声明一块存储空间 |
| **volumeMounts** | 容器字段（容器级别） | 把 volume 挂载到容器路径 |
| **mountPath** | volumeMounts 的子字段 | 挂载到容器里的目标目录 |
| **containers** | Pod 字段 | Pod 里的容器列表 |
| **tmpfs** | Linux 内存文件系统 | Secret 在节点上的默认存储位置 |
