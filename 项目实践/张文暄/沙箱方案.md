# 基于docker容器运行时的沙箱方案（单节点）

![](C:\Users\pc\Pictures\Screenshots\屏幕截图 2026-05-20 093344.png)

如图所示，本k8s集群的**容器运行时是docker**，其具体的容器运行时调用架构如下所示：
- 旧Docker：kubelet → dockershim → docker → containerd → runc → 内核(namespace+cgroup)

- **底层执行层视角（实际干活的）**

  在宿主机上，如果执行 `ps aux | grep containerd`命令，能看到大量的 `containerd-shim-runc-v2`进程正在运行。这说明 Docker 接收到 Kubelet 的指令后，并没有亲自去操作容器，而是将任务交给了它内部依赖的、更底层的容器引擎 Containerd 去执行。

而**容器运行时为continerd**架构如下所示：
- 新：kubelet → CRI接口 → containerd → pause容器 → runc → Linux内核(namespace+cgroup)

综上，Docker 本身不支持通过标准的 CRI 接口直接调用像 Kata Containers这样的沙箱运行时。Kata 需要与实现了 CRI 的运行时（如 containerd或 CRI-O）才能够深度集成。

所以，要在 Docker 环境下引入沙箱，必须选择一个 Docker 原生支持的运行时。而 **gVisor** (runsc) 正是 Docker 官方支持的几种运行时引擎之一，可以像 runc（默认运行时）一样被 Docker 直接调用，无需改变底层架构。**！！！（注：但由于dockershim中间件无法识别新的runsc（gVisor）最终也会失败，详细说明在后续内容）！！！**

##三：切换方案（将底层的docker运行时切换到containerd运行时）
### 1.1 目标

在不重装集群的前提下，将容器运行时从 **Docker（dockershim）** 切换为 **Containerd + runc + runsc（gVisor）**，并满足：
- K8s 1.22 官方兼容
- Ubuntu 22.04 systemd cgroup
- 国内镜像加速
- 私有化交付环境稳定

### 1.2 适用范围

- 单 Master 节点
- kubeadm 部署
- flannel / calico CNI
- 允许短暂停服（节点 Drain）

### 3. 切换流程（严格执行顺序）

#### 步骤 1：标记节点不可调度

```shell
NODE=$(hostname)
kubectl drain "$NODE" \
  --ignore-daemonsets \
  --delete-emptydir-data
```

预期：非 DaemonSet Pod 变为 `Pending`

为了安全切换容器运行时，先执行 `kubectl drain`将节点标记为不可调度，并优雅终止非 DaemonSet Pod，避免在停止 kubelet/docker、启动 containerd 的过程中出现 Pod 反复创建、挂载残留或网络 namespace 冲突，确保切换过程可控、可预测


#### 步骤 2：停止 Docker 与 Kubelet

```shell
systemctl stop kubelet
systemctl stop docker
systemctl disable docker
```

清理残留进程：

```shell
pkill -9 dockerd || true
pkill -9 containerd || true
sleep 2
```

- `systemctl stop kubelet`：防止 kubelet 在运行时切换期间继续创建/删除 Pod、调用容器运行时，避免状态不一致。
- `systemctl stop docker`：停用旧运行时，释放相关资源（网络、sock、mount 等）。
- `systemctl disable docker`：避免重启后 docker 自启，导致又走回 dockershim/旧路径。
- `pkill -9 dockerd / containerd`：清理可能残留的守护进程（例如 docker 拉起的 containerd、孤儿进程），减少 socket/端口冲突与“两个 containerd”问题。
- `sleep 2`：给进程退出、文件描述符回收、sock 清理留出时间，降低后续启动新运行时出现异常的概率。

#### 步骤 4：生成并写入标准配置（核心配置）

```shell
mkdir -p /etc/containerd
containerd config default > /etc/containerd/config.toml
```

**写入最终配置（完整、无省略）：**

```yaml
version = 2

[plugins."io.containerd.grpc.v1.cri"]
  sandbox_image = "registry.aliyuncs.com/google_containers/pause:3.8"

  [plugins."io.containerd.grpc.v1.cri".containerd]
    snapshotter = "overlayfs"

    [plugins."io.containerd.grpc.v1.cri".containerd.runtimes]
      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
        runtime_type = "io.containerd.runc.v2"
        [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
          SystemdCgroup = true

      [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
        runtime_type = "io.containerd.runsc.v1"

  [plugins."io.containerd.grpc.v1.cri".registry.mirrors]
    [plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
      endpoint = ["https://docker.m.daocloud.io"]
    [plugins."io.containerd.grpc.v1.cri".registry.mirrors."registry.k8s.io"]
      endpoint = ["https://registry.aliyuncs.com/google_containers"]
```

下面我**逐行、逐块、结合你这个 K8s 1.22 + Ubuntu 22.04 + 单节点集群**来解释：

**为什么必须这样写，不这样写会怎样，以及每一块在“真实生产里”的意义。**


#####一、为什么第一行必须是 `version = 2`
```shell
version = 2
```
###### 它在告诉 containerd 什么？
- 这是 **containerd 配置文件的语法版本**
- `version = 2`对应 **containerd 1.4+ / 1.6 / 1.7**
- K8s 1.20+ 官方推荐、也是唯一长期支持的版本
###### 不写/写错会怎样？
- containerd **直接拒绝启动**
- kubelet 连不上 CRI → 节点 `NotReady`
- 你之前遇到的 `crictl info`失败、sandbox 起不来，很多就是因为这个
**结论：这是地基，不写不行。**


##### 二、`[plugins."io.containerd.grpc.v1.cri"]`是什么？
```shell
[plugins."io.containerd.grpc.v1.cri"]
```
######它是干嘛的？
- 这是 **Kubelet 与 containerd 之间的“翻译官”**
- K8s 不直接操作 containerd
- 它通过 **CRI（Container Runtime Interface）插件** 来沟通
###### 如果删掉会怎样？
- Kubelet 找不到 CRI
- 所有 Pod 无法创建
- 节点直接 `NotReady`
**结论：这是整个 K8s 容器运行时的入口。**


##### 三、`sandbox_image`
```shell
sandbox_image = "registry.aliyuncs.com/google_containers/pause:3.8"
```
###### 它是什么？
- **Pause 容器**
- 每一个 Pod 启动前，**第一个启动的容器**
- 它的作用：**持有 Pod 的 Network Namespace**
	所有业务容器（nginx、mysql、redis…）都会：
- join 到这个 pause 容器的网络
- 共享 IPC / PID namespace
###### 为什么一定要改？
K8s 默认是：
```shell
registry.k8s.io/pause:3.8
```
但在国内：拉不动，超时，直接导致所有 Pod 卡在 `ContainerCreating`
###### 不改的后果
- 控制平面能起来
- 业务 Pod 永远起不来
- 你会花两天查“为什么 Pod 创建不了”
**结论：不改 = 集群瘫痪。**

##### 四、`snapshotter = "overlayfs"`（性能与稳定性）
```shell
[plugins."io.containerd.grpc.v1.cri".containerd]
  snapshotter = "overlayfs"
```
###### 它是干嘛的？
- 决定 **镜像层怎么存储**
- overlayfs 是目前：性能最好，最稳定，最广泛支持

###### 用别的会怎样？
- devicemapper：慢、复杂、易炸
- btrfs / zfs：依赖特定文件系统
- aufs：已淘汰
**结论：Ubuntu 22.04 + K8s = overlayfs 是唯一正确选择。**

##### 五、`runtimes.runc`
```shell
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc]
  runtime_type = "io.containerd.runc.v2"
```
#######  它是什么？
- 99% Pod 使用的运行时
- 直接跟 Linux 内核打交道
- 负责：clone，namespaces，cgroups，chroot

####### `runtime_type = io.containerd.runc.v2`
这是 **K8s 官方推荐**支持：
  - systemd cgroup
  - 更好的生命周期管理
  - 更强的兼容性
**结论：没有 runc，K8s 没法跑 Pod。**

##### 六、`SystemdCgroup = true`（排错排最久的一块）
```shell
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  SystemdCgroup = true
```
###### 它在对齐什么？
- Ubuntu 22.04 **默认用 systemd 管理 cgroup**
- kubelet **默认用 systemd**
- containerd **默认用 cgroupfs**
###### 如果不一致会怎样？
- kubelet 说：我用 systemd 管资源
- containerd 说：我用 cgroupfs 管资源
- 结果：Pod 起不来，节点 NotReady
**结论：K8s 1.22 + Ubuntu 22.04 = 必须 true。**

##### 七、`runsc`（gVisor 沙箱，加分项）
```shell
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
  runtime_type = "io.containerd.runsc.v1"
```
######它是什么？
- Google 的 **用户态内核沙箱**
- 容器系统调用不直接进宿主机内核
- 用于：多租户，不可信代码，防容器逃逸

#######什么时候用？
- 不是默认
- 只在 Pod 里指定：
```shell
runtimeClassName: gvisor
```
✅ **结论：这是安全增强，不是必须，但有它更专业。**


##### 八、`registry.mirrors`（解决 ImagePullBackOff 的根本）
```shell
[plugins."io.containerd.grpc.v1.cri".registry.mirrors]
```
######docker.io
```shell
endpoint = ["https://docker.m.daocloud.io"]
```
- 拉 nginx / mysql / redis 时
- 不走 `registry-1.docker.io`
- 走国内加速

######registry.k8s.io
```shell
endpoint = ["https://registry.aliyuncs.com/google_containers"]
```
- 拉 pause / coredns / kube-proxy 时
- 不走国外 k8s 官方仓库
- 走阿里云
######不加的后果
- 控制平面镜像拉不动
- 业务镜像拉不动
- **国内环境 = 必须加**

该配置基于 containerd v2 语法，启用 CRI 插件，统一使用 systemd cgroup 管理资源，指定国内可访问的 pause 镜像与镜像加速源，并以 runc 作为默认运行时、runsc 作为可选安全沙箱，满足 K8s 1.22 在 Ubuntu 22.04 环境下的生产级运行要求。

## 一、先给结论（关系图）

Linux 内核
 └── cgroup（内核功能，资源限制能力）
     ├── cgroupfs（直接写 /sys/fs/cgroup，老方式）
     └── systemd（通过 systemd 接口写 cgroup，新/主流方式）

systemd（PID 1）
 ├── 管理服务（kubelet/containerd/docker）
 └── 管理 cgroup（资源限制）
 
---
## 二、cgroup 是什么（核心）
**cgroup = Linux 内核功能**  
作用：限制、统计、隔离进程资源（CPU / 内存 / pid / io…）

- 它不是“一个服务”
- 它不是“一个软件”
- 是 **内核里的机制**

真正干活的是 **内核**，cgroup 只是内核提供的能力。


## 三、cgroupfs 是什么？
**cgroupfs = 直接操作 cgroup 的方式（接口）**

- 表现：写文件
  /sys/fs/cgroup/cpu/my-pod

- 谁会用：
  - 老容器运行时
  - 老系统
  - 设置 `SystemdCgroup=false`

特点：
- 简单
- 但容易和 systemd 冲突（两个管家抢一个目录）

---

## 四、systemd 在这里扮演什么？
**systemd 两个角色：**

1) **PID 1（服务管理器）**  
- 启动/停止 kubelet、containerd  
- 你用的 `systemctl`

2) **cgroup 管理者（在支持的系统上）**  
- 内核提供 cgroup
- systemd 作为“统一管理员”去：
  - 创建 cgroup 层级
  - 设置 cpu/memory
  - 给服务/Pod 归属

当你设置：
SystemdCgroup = true

意思是：
> “runc，别自己写 /sys/fs/cgroup(不要用cgroupfs的方式)，让 systemd 去写。”

---

## 五、为什么 K8s 要选 systemd 而不是 cgroupfs？
Ubuntu 22.04：
- 默认由 systemd 管理 cgroup
- 如果 runc 用 cgroupfs：
  - systemd 建的 cgroup 目录
  - runc 往里写 / 建子目录
  - 路径/权限/层级容易不一致 → Pod 起不来

所以 K8s 官方推荐：
> kubelet(cgroupDriver=systemd) + runc(SystemdCgroup=true)

---

## 六、一句话最清楚的说法（面试/文档）
> cgroup 是 Linux 内核的资源限制机制；cgroupfs 是直接通过文件系统操作 cgroup 的方式，systemd 则可作为 cgroup 的管理者，通过自身接口统一创建和配置 cgroup；在 Kubernetes 节点上，kubelet 的 cgroupDriver 与容器运行时（如 runc 的 SystemdCgroup）必须一致，通常都选择 systemd 以避免冲突。

## 六、常见问题速查表

| 现象                     | 原因                 | 解决                  |
| ------------------------ | -------------------- | --------------------- |
| Node NotReady            | SystemdCgroup=false  | 检查 runc.options     |
| Pod 卡 ContainerCreating | sandbox_image 拉不到 | 换成 aliyun pause     |
| ImagePullBackOff         | mirrors 未生效       | 检查 registry.mirrors |
| kubelet 起不来           | socket 路径错        | 核对 containerd.sock  |

本次切换采用 **K8s 官方推荐的 CRI 模式**，移除 Dockershim，使用 Containerd 作为统一容器运行时，并开启 `SystemdCgroup=true`与国内镜像加速，满足生产级稳定性与私有化交付要求。



如果集群失败则被迫进行回滚操作，换回原来的容器运行时docker

```shell
# 1. 停 kubelet
systemctl stop kubelet

# 2. 停 containerd（防止并存）
systemctl stop containerd
systemctl disable containerd

# 3. 清理可能残留的 containerd sock
rm -f /run/containerd/containerd.sock

# 4. 恢复 kubelet 配置（指向 docker）
cp /var/lib/kubelet/kubeadm-flags.env.bak /var/lib/kubelet/kubeadm-flags.env

# 5. 启动 docker
systemctl start docker
systemctl enable docker

# 6. 启动 kubelet
systemctl start kubelet
systemctl enable kubelet

# 7. 等待并验证
sleep 70
kubectl get nodes
kubectl get pods -n kube-system
```

补：当关闭虚拟机，第二次启动时kubernetes 节点（k8s-master-shizai）状态异常，kubectl get nodes无法获取信息
kubelet服务日志持续报错：Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?
故障原因分析
- Kubelet 依赖的容器运行时服务（Docker Daemon / dockerd）未运行
- Kubelet 的配置（/var/lib/kubelet/kubeadm-flags.env）使其依赖于 Docker 作为容器运行时
- 当 Kubelet 启动时，无法连接到其指定的运行时端点（Docker 的套接字），因此启动失败，导致节点代理失活，整个节点脱离集群管理。
- 需要设置开机自启：systemctl enable docker/kubelet


##二、总结
###方案一：在现有 Docker运行时 + dockershim 架构上，使用gVisor方案

目标：在现有 Kubernetes 集群（使用 Docker 作为容器运行时）上，通过配置 Docker 来支持 gVisor (runsc)。

失败原因：架构性限制，无法绕过。

Kubernetes 通过一个名为 **dockershim** 的内置组件与 Docker 通信，dockershim是一个已废弃的适配器，其功能是固化的，它不支持识别或转发非默认的运行时处理器。因此，尽管成功在 Docker 的配置（/etc/docker/daemon.json）中注册了 runsc运行时，但当 Kubernetes (kubelet) 尝试通过 dockershim创建指定了 runtimeClassName: gvisor的 Pod 时，dockershim无法理解此请求，直接返回错误：RuntimeHandler "runsc" not supported。这并非配置错误，而是所用 Kubernetes 版本（1.22）中该架构的固有缺陷。

### 方案二：切换到 Containerd 作为 CRI 运行时

目标：将集群的容器运行时从 Docker 迁移到 Containerd，因为 Containerd 原生支持 CRI 接口，可以完美集成 gVisor。

失败原因：执行过程中的环境与依赖问题。

核心障碍：镜像拉取失败。在切换运行时后，kubelet需要重新创建所有 Kubernetes 系统组件（控制平面 Pod）。这首先需要从网络拉取基础镜像（如 pause:3.8）。由于 网络访问限制，containerd无法从默认的境外镜像仓库（registry.k8s.io）成功拉取镜像，导致控制平面无法启动，集群完全不可用。虽然后来通过特定（科学上网）方式解决了 pause镜像的拉取，但可能还有其他组件镜像或后续依赖问题。

控制平面组件不稳定，在解决基础镜像问题后，控制平面组件（如 kube-apiserver）在启动过程中出现了与 etcd存储交互的问题（如 StorageError: key not found），导致组件进入崩溃循环 (CrashLoopBackOff)，这可能是由于在反复切换、重启过程中，组件状态、证书验证或网络连接出现瞬时异常所致，最后立刻恢复到docker运行时（**生产环境下一定要备份修改前的配置文件**）

一旦能确保 containerd拥有稳定、可达的镜像源，并保证在切换过程中控制平面组件的存储和网络依赖稳定

##三、理论上正确的gVisor流程

要成功部署一个使用gVisor沙箱的Pod，**核心前提是Kubernetes集群必须使用containerd作为容器运行时**，而非Docker。因为Docker通过dockershim与Kubelet通信的架构无法支持自定义的CRI运行时处理器（如runsc）。以下是在containerd环境下部署gVisor Pod的完整流程与测试方法。

### **第一步：环境准备与前提确认**

1. **确认容器运行时**：确保所有节点均已切换至containerd。

```shell
   # 在节点上执行
   kubectl describe node <节点名称> | grep "Container Runtime"
   # 应显示：Container Runtime: containerd://<版本号>
```

   如果仍显示`docker://`，需要先完成从Docker到containerd的迁移。这涉及节点腾空、修改kubelet配置等操作，风险较高，需在维护窗口进行。

2. **安装gVisor (runsc)**：如果尚未安装，在**每个**工作节点上执行。

```
   # 1. 下载runsc（选择适合您架构的版本，此处以amd64为例）
   # 官方源（需外网）
   wget https://storage.googleapis.com/gvisor/releases/release/latest/amd64/runsc
   # 或使用备用源/内网预置包
   # wget <您的内网地址>/runsc
   
   # 2. 安装
   sudo install -m 755 runsc /usr/local/bin/
   
   # 3. 验证安装
   sudo runsc --version
   # 应输出类似：runsc version release-20240506.0
```

### **第二步：配置containerd以识别gVisor运行时**

在每个节点上修改containerd的配置文件（通常为`/etc/containerd/config.toml`）。

1. **生成默认配置**（如果文件不存在）：

```shell
   sudo containerd config default | sudo tee /etc/containerd/config.toml
```

2. **添加gVisor运行时配置**：
使用`sudo vim /etc/containerd/config.toml`编辑文件，找到 `[plugins."io.containerd.grpc.v1.cri".containerd.runtimes]`部分，在已有的 `runc`配置块**之后**，添加以下配置：

```shell
   [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runsc]
     runtime_type = "io.containerd.runsc.v1"
     # 可选：配置root路径，保持默认即可
     # root = "/run/containerd/runsc"
```

3. **重启containerd**以加载新配置：

```shell
   sudo systemctl restart containerd
   sudo systemctl status containerd # 确认服务运行正常
```

### **第三步：在Kubernetes中创建RuntimeClass**

RuntimeClass是Kubernetes中用于选择容器运行时的资源。创建一个定义gVisor运行时的RuntimeClass。

1. **创建RuntimeClass YAML文件**（例如 `gvisor-runtimeclass.yaml`）：

```yaml
apiVersion: node.k8s.io/v1
kind: RuntimeClass
metadata:
  name: gvisor  # 这个名称将在Pod中引用
handler: runsc  # 必须与containerd配置中定义的运行时名称完全一致
```

2. **应用到集群**：

```shell
   kubectl apply -f gvisor-runtimeclass.yaml
   kubectl get runtimeclass  # 确认创建成功
```

### **第四步：部署并使用gVisor运行时的测试Pod**

1. **创建测试Pod的YAML文件**（例如 `test-gvisor-pod.yaml`）：

  # 为此 Pod 指定的唯一名称，在同一个命名空间内不能重复。
  # 您将使用此名称（gvisor-test-pod2）来管理（查看、删除、进入）这个 Pod。

    # 在您的离线环境中，此地址必须与通过 `ctr -n k8s.io images ls` 查看到的、已导入本地的镜像地址**完全一致**。

    # 2. `sleep 3600` 让容器进程保持运行 1 小时，防止其执行完 `echo` 后立即退出，方便您调试和进入。

      runAsNonRoot: false

### 二、核心问题详解：为什么原来的 `runsc`没有对应的 `shim`？

原因可以归结为 **“获取了错误的二进制文件组合”**。
1. **`runsc`与 `containerd-shim-runsc-v1`是两个独立文件**：
   - **`runsc`**：是 gVisor 的**核心引擎**，负责创建和管理沙箱环境。
   - **`containerd-shim-runsc-v1`**：是一个**“垫片”或“适配器”**。它的唯一职责是作为 `containerd`和 `runsc`之间的桥梁，按照 `containerd`的 shim v2 API 规范进行通信（例如，接收 `-namespace`等参数）。

2. **遇到的问题根源**：
   通过 `md5sum`对比，发现最初的 `/usr/bin/containerd-shim-runsc-v1`和 `/usr/bin/runsc`的 MD5 值**完全相同**。这证明当时的 `shim`文件只是 `runsc`的一个**副本**，而不是一个实现了 containerd shim 接口的独立程序。

   - **导致结果**：当 `containerd`尝试调用这个“假 shim”时，传递了标准的 `-namespace`参数，而“假 shim”（本质上是 `runsc`）无法识别此参数，于是报错 `flag provided but not defined: -namespace`，Pod 状态永久卡在 `ContainerCreating`。

3. **为何会发生这种情况？**

   - **来源不可靠**：您最初可能通过非官方渠道（如直接下载不完整的发布包、从某些镜像站获取了版本不匹配或损坏的文件）获得了 `runsc`二进制文件，并且这个渠道没有提供独立的 `shim`文件。

   - **手动补救失误**：在排错过程中，可能尝试过将 `runsc`复制为 `containerd-shim-runsc-v1`作为权宜之计，但这无法解决根本问题，因为两者功能不同。

   - **APT 源拯救了一切**：当最终通过 `sudo apt-get install runsc`从 **gVisor 官方维护的 APT 仓库** 安装时，安装包 (`runsc_20260520.0_amd64.deb`) 内**同时包含了正确且匹配的 `runsc`和 `containerd-shim-runsc-v1`两个独立二进制文件**。安装后，两者的 MD5 值不同，证明了它们是各自独立、功能完整的文件。

### 三、总结与最终验证建议
**总结**：成功根本在于通过官方 APT 源完成了完整、正确的安装，获得了“真 shim”，从而打通了 `containerd`到 `runsc`的最后一公里。

##四、KATA方案

除了gVisor，还有KATA
KATA和gVisor一样，都是基于kubelet → CRI接口 → containerd → pause容器 → runc → Linux内核(namespace+cgroup)部署的

Kata Containers 的部署是一个系统性的过程，其核心在于**将 Kata 作为 containerd 的一个可选的运行时处理器（runtime handler）进行配置**，并最终通过 Kubernetes 的 `RuntimeClass`供 Pod 选择使用。以下是基于官方文档和社区实践总结的通用部署流程。

### 部署前提与架构基础

在开始前，请确保您的环境满足以下条件，这是部署成功的基石：

1. **容器运行时**：Kubernetes 集群**必须**使用 **containerd** 作为容器运行时，而非 Docker。这是集成 Kata 或 gVisor 等沙箱技术的**强制性前提**。
2. **硬件与内核**：

   - **虚拟化支持**：Kata 依赖硬件虚拟化技术（如 Intel VT-x 或 AMD-V）。请通过 `grep -E '(vmx|svm)' /proc/cpuinfo`命令确认 CPU 支持，并确保 `kvm`内核模块已加载，需要在主机和虚拟机中进行一些关于虚拟化的设置，重启后如果无法访问api-server，执行`systemctl restart docker`和`systemctl restart kubelet`
3. **Kubernetes 版本**：建议使用 1.20 及以上版本，以稳定支持 `RuntimeClass`功能。

### 核心部署步骤

整个部署过程可以概括为以下四个主要阶段：

#### 阶段一：安装 Kata Containers 组件

1. **下载与解压**：从 [Kata Containers GitHub Releases](https://github.com/kata-containers/kata-containers/releases)页面下载最新的稳定版二进制包（例如 `kata-static-<version>-x86_64.tar.xz`）。

2. **安装到系统**：将压缩包解压到根目录，其文件会自动部署到 `/opt/kata/`目录下。

```bash
sudo tar -C / -xJf kata-static-<version>-x86_64.tar.xz
```

3. **验证安装**：运行 `kata-runtime --version`和 `kata-runtime check`来检查安装是否成功及系统环境是否满足要求。

#### 阶段二：配置 containerd 以识别 Kata 运行时

这是最关键的一步，需要修改 containerd 的配置文件（通常位于 `/etc/containerd/config.toml`）。

1. **生成默认配置**（如果文件不存在）：

```bash
sudo containerd config default > /etc/containerd/config.toml
```

2. **添加 Kata 运行时配置**：在 `config.toml`文件的 `[plugins."io.containerd.grpc.v1.cri".containerd.runtimes]`部分，添加 `kata`运行时配置。

```toml
   [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata]
     runtime_type = "io.containerd.kata.v2"
     privileged_without_host_devices = true
     [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.kata.options]
       ConfigPath = "/opt/kata/share/defaults/kata-containers/configuration.toml"
```

   - `runtime_type`：必须指定为 `"io.containerd.kata.v2"`。
   - `ConfigPath`：指向 Kata 的默认配置文件路径。

#### 阶段三：重启 containerd 并测试

1. **重启服务**：让 containerd 加载新的配置。

```
sudo systemctl restart containerd
sudo systemctl status containerd  # 确认服务运行正常
```

2. **使用 `ctr`测试 Kata 容器**：通过 containerd 的命令行工具直接运行一个 Kata 容器，验证集成是否成功。

```
sudo ctr image pull docker.io/library/busybox:latest
sudo ctr run --runtime io.containerd.kata.v2 --rm -t docker.io/library/busybox:latest kata-test uname -r
```

**成功标志**：该命令输出的内核版本应与主机内核版本**不同**，这表明容器运行在 Kata 提供的独立虚拟机内核中。

#### 阶段四：在 Kubernetes 中创建 RuntimeClass

至此，Kata 已在节点层面就绪。最后一步是让 Kubernetes 知道这个新运行时。

1. **创建 RuntimeClass 资源**：定义一个名为 `kata`的 RuntimeClass。

```
   # kata-runtimeclass.yaml
   apiVersion: node.k8s.io/v1
   kind: RuntimeClass
   metadata:
     name: kata
   handler: kata  # 此名称必须与 containerd 配置中定义的运行时名称一致
```

2. **应用到集群**：

```
kubectl apply -f kata-runtimeclass.yaml
```

3. **指定 Pod 使用 Kata**：在需要强隔离的 Pod 的 `spec`中，指定 `runtimeClassName`。

```
   apiVersion: v1
   kind: Pod
   metadata:
     name: nginx-kata
   spec:
     runtimeClassName: kata  # 关键：指定使用 kata 运行时
     containers:
     - name: nginx
       image: nginx:alpine
```

### 总结与注意事项

- **路径依赖**：上述步骤假设 Kata 安装在 `/opt/kata`。如果路径不同，请相应调整 `ConfigPath`和系统 `PATH`。

- **配置检查**：Kata 自身有丰富的配置文件（`configuration.toml`），可用于调整虚拟化器（QEMU、Cloud Hypervisor 等）、内存和 CPU 设置。

- **网络与存储**：Kata 容器通常使用 `virtio-fs`进行文件共享，网络则通过 CNI 插件与 Kubernetes 网络集成，这些在默认配置中均已处理。

- **多节点部署**：需要在**每个**工作节点上重复执行上述安装与配置步骤。

完成以上步骤后，Kubernetes 集群就具备了运行强隔离的 Kata 容器的能力。可以通过 `kubectl describe pod <pod-name>`查看事件，或通过 `kubectl exec`执行 `uname -r`来确认 Pod 是否运行在 Kata 沙箱内。

# 五、逻辑沙箱

------

### 阶段一：沙箱基建（Namespace & Quota）

**目标**：创建一个独立的环境，并给它设定“资源预算”。

1. **创建命名空间 (Namespace)**

   *逻辑上的资源隔离边界，相当于给租户建了一个专属的“院子”。*

```bash
kubectl create namespace practice
```

2. **设置资源配额 (ResourceQuota)**

   *给这个院子加上“硬性消费上限”，防止院子里的应用把整个集群的资源吃光。*

```yaml
   # namespace/practice-quota.yaml
   apiVersion: v1
   kind: ResourceQuota
   metadata:
     name: practice-quota
     namespace: practice
   spec:
     hard:
       requests.cpu: "2"
       requests.memory: 2Gi
       limits.cpu: "4"
       limits.memory: 4Gi
       pods: "10"
```

```shell
kubectl apply -f namespace/practice-quota.yaml
```

`requests.memory: 2Gi`
**含义**：
- 所有 Pod **请求的内存总和 ≤ 2 GiB**
**作用**：
- 保证调度时不把节点内存打爆
- 防止“看起来没跑啥，但节点却 OOM”的情况

`requests.memory: 2G`
**含义**：
- 所有 Pod 请求的内存总和 ≤ 2 GiB
**作用**：
- 保证调度时不把节点内存打爆
- 防止“看起来没跑啥，但节点却 OOM”的情况

`limits.cpu: "4"`
**含义**：
- 所有 Pod CPU 使用上限总和 ≤ 4 核
**区别**
类型				 作用
requests.cpu	调度时保证
limits.cpu		  运行时封顶

`limits.memory: 4Gi`
**含义**:
- 所有 Pod 内存使用上限总和 ≤ 4 GiB
- 一旦某个 Pod 内存超过自己的 limits.memory
- 直接 OOMKill（你刚刚亲手验证过）

`pods: "10"`
**含义**：
- 该namespace中最多有10个pod


### 阶段二：完善约束（LimitRange 补漏）

**目标**：解决“配额存在，但无法有效管控单容器资源”的痛点。

1. **遭遇痛点（混沌测试）**
	直接for循环创建了不带资源**没有resources**声明的 Pod，结果 K8s 毫不留情地报错：
```bash
for i in {1..10}; do
  kubectl run test-$i \
    --image=nginx \
    --restart=Never \
    -n practice
done
```

   `Error from server (Forbidden): must specify limits.cpu, limits.memory...`

*这证明了 K8s 的配额拦截机制是生效的，但也暴露了每次手写 resources 太繁琐。*

**为什么会这样？**
- 核心原因：准入控制器（Admission Controller）的“硬性做账”
	- 当在一个 Namespace 中创建了包含 CPU 或 Memory 限制的 ResourceQuota后，Kubernetes 会自动触发一个叫做 ResourceQuota Admission Controller（资源配额准入控制器）的机制
	- 这个控制器的职责只有一个：在 Pod 被创建之前，严格审查它的“资源账单”。
	- 它的审查逻辑是这样的：
		1. 计算已用资源：K8s 会把当前 Namespace 下所有已存在的 Pod的 requests和 limits加起来，算出当前总共用了多少。
		2. 计算新 Pod 的资源：当你的新 Pod 没有声明 resources时，K8s 就无法知道这个 Pod 到底要用多少 CPU 和内存。
		3. 对比配额上限（Hard）：因为不知道新 Pod 用多少，K8s 就无法判断如果允许它创建，会不会导致整个 Namespace 突破 ResourceQuota设定的上限。
		4. 拒绝请求：为了绝对的安全，防止资源被偷偷“偷渡”使用，K8s 会直接返回一个 Forbidden错误，拒绝创建这个 Pod。

2. **部署默认资源配置 (LimitRange)**

   *相当于给院子里定下规矩：“只要进来的容器，默认都给他们分配这么多LimitRange的资源”。完美解决了手动声明繁琐的问题。*

```yaml
   # namespace/practice-limitrange.yaml
   apiVersion: v1
   kind: LimitRange
   metadata:
     name: practice-limit
     namespace: practice
   spec:
     limits:
     - default:
         cpu: "200m"
         memory: "256Mi"
       defaultRequest:
         cpu: "100m"
         memory: "128Mi"
       type: Container
```

```bash
   kubectl apply -f namespace/practice-limitrange.yaml
```

### 总结

回顾今天的全过程，实际上只用了三个 K8s 原生对象
- **Namespace**：负责逻辑归类
- **ResourceQuota**：负责宏观的总量控制
- **LimitRange**：负责微观的单实例兜底
