# 阶段一：VLAN / Access / Trunk —— 从电信号讲起

## 1.1 最底层：交换机到底在干什么？

### 物理层：电信号与MAC地址

想象你是一个交换机，你面前有24根网线。每根网线上有电信号在跑。你的工作很简单：

> **从某个口收到一个数据帧，看看它的"目标MAC地址"，然后从正确的口转发出去。**

```
┌──────────────────────────────────────────────┐
│               以太网帧结构                      │
│                                                │
│  前导码 │ 目标MAC │ 源MAC │ 类型 │ 数据 │ FCS  │
│  8字节  │ 6字节   │ 6字节 │2字节 │46-   │4字节 │
│         │        │       │      │1500  │      │
└──────────────────────────────────────────────┘

MAC地址 = 网卡的"身份证号"，全球唯一，48位
例如：00:1A:2B:3C:4D:5E
```

### 交换机的核心机制：MAC地址表

> 🤝 **相关原理**：关于路由与交换的底层区别，详见 [[网络/TCP-IP详解/路由与交换的核心原理及区别]]

交换机启动时，MAC地址表是空的。它通过一个极其简单但聪明的规则来学习：

```
📌 交换机的两个核心动作：

【学习】：从哪个口收到帧，就把"源MAC + 端口号"记下来
         "哦，MAC地址 AA:BB:CC:DD:EE:01 在 端口1 那边"

【转发】：看目标MAC，查表决定从哪个口出去
         - 查到了 → 单播转发（只从那个口出去）
         - 查不到 → 泛洪（从除收到口外的所有口出去）
         - 目标是广播地址 FF:FF:FF:FF:FF:FF → 泛洪
```

**来看一个实际过程：**

```
初始状态：MAC表为空

时刻1：PC1（MAC:AA:01）从端口1 发帧给 PC2（MAC:BB:02）
  → 学习：记录 {AA:01, 端口1}
  → 转发：不知道BB:02在哪 → 泛洪到所有端口
  → PC2收到后回复

时刻2：PC2（MAC:BB:02）从端口2 发帧回复 PC1
  → 学习：记录 {BB:02, 端口2}
  → 转发：查表发现AA:01在端口1 → 只从端口1出去

✅ 现在MAC表：
  AA:01 → 端口1
  BB:02 → 端口2
```

## 1.2 为什么需要VLAN？—— 广播风暴的噩梦

### 问题的本质

交换机有一个"先天缺陷"：**广播帧会泛洪到所有端口**。

想象一个有200台电脑的平面网络：

```
200台PC在同一个交换机网络中

PC1 发送 ARP请求（广播）："谁是 192.168.1.100？"
  → 交换机泛洪到199个端口
  → 199台PC都收到并处理这个帧
  
如果每秒有1000个广播帧...
  → 每台PC每秒要处理 1000 个不相关的广播帧
  → CPU飙升，网络瘫痪 → 这就是"广播风暴"
```

### VLAN的解决方案

**VLAN（Virtual LAN）= 把一个物理交换机，逻辑上切成多个独立的虚拟交换机**（相关实操指南：[[网络/网络排障/网络工程与 VLAN 规划实操指南（思科 Cisco 版本）|VLAN 规划与 Cisco 配置]]）

```
没有VLAN：                          有VLAN：
┌─────────────────┐                ┌─────────────────┐
│                 │                │  VLAN 10 │ VLAN 20│
│  所有端口在     │                │  端口1-12│端口13-24│
│  同一个广播域   │                │  ↕         ↕     │
│                 │                │ 研发部     市场部  │
│  广播帧→所有端口│                │                   │
│                 │                │ 广播帧→只在同VLAN内│
└─────────────────┘                └─────────────────┘
```

### 🔬 底层原理：802.1Q标签

VLAN是怎么实现的？关键在于**在以太网帧里插入一个4字节的"标签"**：

```
原始帧：
┌────────┬─────────┬───────┬──────┬──────┬─────┐
│ 前导码  │ 目标MAC │ 源MAC │ 类型 │ 数据 │ FCS │
└────────┴─────────┴───────┴──────┴──────┴─────┘

插入802.1Q标签后：
┌────────┬─────────┬───────┬──────────────┬──────┬──────┬─────┐
│ 前导码  │ 目标MAC │ 源MAC │ 802.1Q标签   │ 类型 │ 数据 │ FCS │
│        │         │       │ (4字节)      │      │      │     │
└────────┴─────────┴───────┴──────────────┴──────┴──────┴─────┘

802.1Q标签的4字节：
┌──────────────┬──────────┬───────────┬────────────┐
│ TPID (2字节)  │ PRI(3bit)│ CFI(1bit) │ VID(12bit) │
│ 固定0x8100   │ 优先级    │ 规范格式   │ VLAN ID    │
│ "我是标签帧"  │ 0-7      │           │ 1-4094     │
└──────────────┴──────────┴───────────┴────────────┘

VID=10 → 这个帧属于VLAN 10
```

> **关键理解**：VLAN ID占12位，所以最多支持 2^12 - 2 = 4094 个VLAN（0和4095保留）。

### 交换机的内部处理流程（这是最重要的原理！）

```
帧进入交换机后的完整处理流程：

    ┌─────────┐
    │ 帧到达   │
    │ 端口X   │
    └────┬────┘
         │
         ▼
    ┌─────────────────────┐
    │ 端口X是什么链路类型？ │
    └────┬────────────────┘
         │
    ┌────┴────────────────────────────────┐
    │                                     │
    ▼                                     ▼
 Access端口                         Trunk端口
    │                                     │
    │ ①收到无标签帧                       │ ①收到有标签帧
    │   → 打上PVID（端口默认VLAN）        │   → 检查VID是否在允许列表中
    │                                     │     允许 → 继续处理
    │ ②收到有标签帧                       │     不允许 → 丢弃
    │   → VID=PVID → 接受                │
    │   → VID≠PVID → 丢弃               │ ②收到无标签帧
    │                                     │   → 打上PVID
    └──────────┬──────────────────────────┘
               │
               ▼
    ┌─────────────────────┐
    │ 查看目标MAC + VID   │
    │ 查MAC地址表         │
    │ (注意：MAC表是按     │
    │  VLAN隔离的！)      │
    └──────────┬──────────┘
               │
               ▼
    ┌─────────────────────┐
    │ 从目标端口发出      │
    │ 发出前：             │
    │ Access口→剥掉标签   │
    │ Trunk口→             │
    │   VID=PVID→剥掉标签 │
    │   VID≠PVID→保留标签 │
    └─────────────────────┘
```

## 1.3 Access端口 vs Trunk端口 —— 终于明白了

### 为什么需要两种端口？

```
场景：
PC1 ──(网线)── 交换机SW1 ──(网线)── 交换机SW2 ──(网线)── PC2

问题1：PC不认识VLAN标签！
  → PC发出的帧没有标签
  → 发给PC的帧也不能带标签（PC看不懂会丢弃）
  → 所以连接PC的端口 → 发出时必须"剥掉标签" → 这就是 Access

问题2：交换机之间要传递多个VLAN的流量
  → SW1的VLAN 10和VLAN 20的帧都要到SW2去
  → 必须"带着标签"传输，否则SW2不知道帧属于哪个VLAN
  → 所以交换机之间的端口 → 发出时"保留标签" → 这就是 Trunk
```

### 图解对比

```
Access端口（连接终端设备）：
                                   
 PC1 ──无标签帧──→ [Access口] ──打标签(VLAN10)──→ 交换机内部处理
                      │
                      └── 发出去时：剥掉标签 → PC收到无标签帧 ✅

特点：一个Access口只属于一个VLAN


Trunk端口（连接交换机/路由器）：
                                   
 SW1 ──带标签帧──→ [Trunk口] ──检查允许列表──→ 转发到SW2
                      
  VLAN 10的帧 → 带Tag VID=10 通过 ✅
  VLAN 20的帧 → 带Tag VID=20 通过 ✅
  VLAN 30的帧 → 不在允许列表   丢弃 ❌

特点：一个Trunk口可以承载多个VLAN的流量
```

### 第二步：在接入交换机上创建VLAN并配置Access端口

```bash
# ========= SW3（A楼1层 - 研发部VLAN10）=========
[SW3] vlan batch 10
# 解读：一次性创建VLAN 10
# 如果需要多个：vlan batch 10 20 30
# 思科：vlan 10 （进入vlan配置模式）

[SW3] interface GigabitEthernet 0/0/1
[SW3-GigabitEthernet0/0/1] port link-type access
# 解读：把这个端口设置为Access模式
# 思科：switchport mode access

[SW3-GigabitEthernet0/0/1] port default vlan 10
# 解读：这个Access端口属于VLAN 10
# 意思是：PC发来的无标签帧，被打上VLAN 10的标签
# 思科：switchport access vlan 10

[SW3-GigabitEthernet0/0/1] quit

# 批量配置多个端口（假设端口1-12都给研发部）
[SW3] interface range GigabitEthernet 0/0/1 to GigabitEthernet 0/0/12
[SW3-if-range] port link-type access
[SW3-if-range] port default vlan 10
[SW3-if-range] quit
```

# 阶段二：VLANIF与三层交换 —— 打通VLAN间的壁垒

## 2.1 为什么需要三层交换？

```
问题：VLAN 10（192.168.10.0/24）和 VLAN 20（192.168.20.0/24）怎么通信？

方案一：用路由器（传统方式，叫"单臂路由"）
  PC1 → SW1 → 路由器 → SW1 → PC2
  问题：所有VLAN间流量都要绕一圈路由器，路由器成为瓶颈

方案二：用三层交换机（现代企业网标配）
  三层交换机 = 二层交换机 + 内置路由器
  在每个VLAN上创建一个"虚拟接口"（VLANIF），给它配IP作为网关
  VLAN间的路由在交换机内部完成，速度极快！
```

## 2.2 底层原理：VLAN间路由的完整过程

```
PC1 (VLAN10, 192.168.10.1) 要访问 PC2 (VLAN20, 192.168.20.1)

┌──────────────────────────────────────────────────────────────┐
│ Step 1: PC1发现目标是不同网段，发给默认网关                    │
│   PC1 思考：                                                  │
│   我的IP: 192.168.10.1/24                                     │
│   目标IP: 192.168.20.1                                        │
│   不在同一网段！→ 发给网关 192.168.10.254                      │
│                                                               │
│ Step 2: PC1 发ARP请求获取网关的MAC地址                         │
│   "谁是 192.168.10.254？"                                     │
│   → 三层交换机的VLANIF 10 回复自己的MAC                       │
│                                                               │
│ Step 3: PC1把帧发给网关                                       │
│   帧：[PC1_MAC → VLANIF10_MAC | IP: 192.168.10.1→192.168.20.1]│
│                                                               │
│ Step 4: 三层交换机内部路由                                     │
│   收到帧 → 解封装到IP层 → 查路由表                            │
│   路由表说：192.168.20.0/24 → 直连 → VLANIF 20               │
│   → 重新封装：[VLANIF20_MAC → PC2_MAC | 同样的IP包]          │
│   → 从VLAN 20的端口发出                                       │
│                                                               │
│ Step 5: PC2收到数据                                           │
└──────────────────────────────────────────────────────────────┘

🔑 关键理解：
  三层交换转发一次，MAC地址会改变两次！
  源MAC从 PC1_MAC → VLANIF10_MAC → VLANIF20_MAC
  但IP地址始终不变：192.168.10.1 → 192.168.20.1
```

# 阶段三：VRRP —— 网关永不宕机的秘密

## 3.1 为什么需要VRRP？

```
问题：如果SW1挂了，所有PC的网关就没了，全网断网！

现状：
  PC的网关指向SW1的VLANIF IP（192.168.10.252）
  SW1宕机 → PC无法发送跨网段数据 → 全网瘫痪

解决：SW1和SW2共同提供一个"虚拟网关"
  
  ┌──────────┐          ┌──────────┐
  │   SW1    │          │   SW2    │
  │ .252     │          │ .253     │
  │          │          │          │
  │  我当Master         │  我当Backup
  │  处理所有流量        │  随时待命
  └────┬─────┘          └────┬─────┘
       │                     │
       └─────────┬───────────┘
                 │
          虚拟IP: .254
          虚拟MAC: 00-00-5E-00-01-{VRID}
          
  PC的网关指向虚拟IP .254
  正常情况下SW1处理，SW1挂了SW2秒级接管
```

## 3.2 VRRP底层原理

```
VRRP工作过程：

1️⃣ 选举Master
   - 比较优先级（默认100，范围1-254）
   - 优先级高的当Master
   - 优先级相同，比IP地址大小
   
2️⃣ Master定期发送VRRP通告（Advertisement）
   - 组播地址：224.0.0.18
   - 协议号：112（VRRP）
   - 默认每1秒发一次
   - 内容：我是Master，优先级是X，虚拟IP是Y

3️⃣ Backup监听通告
   - 如果3×1秒 + 偏移量 没收到通告 → 认为Master挂了
   - Backup升级为新的Master
   - 发送免费ARP（Gratuitous ARP）：
     "虚拟IP .254 的MAC地址是 虚拟MAC"
   - 下游交换机更新MAC表 → 流量切换到新Master

4️⃣ 虚拟MAC地址格式
   00-00-5E-00-01-{VRID的十六进制}
   VRID=1 → 00-00-5E-00-01-01
   
   这就是为什么切换时PC无感知——MAC没变！
```

## 3.3 配置VRRP

```bash
# ========= SW1（配置为Master）=========

# VLAN 10 的VRRP
[SW1] interface Vlanif 10
[SW1-Vlanif10] vrrp vrid 1 virtual-ip 192.168.10.254
# 创建VRRP组1，虚拟IP为.254
# 思科（HSRP，思科的私有协议，功能类似）：
#   standby 1 ip 192.168.10.254

[SW1-Vlanif10] vrrp vrid 1 priority 120
# 设置优先级120（高于默认的100），确保SW1当Master
# 思科：standby 1 priority 120

[SW1-Vlanif10] vrrp vrid 1 preempt-mode timer delay 20
# 抢占模式：如果SW1恢复，等20秒后再抢回Master
# 避免网络抖动时频繁切换
# 思科：standby 1 preempt delay minimum 20

# VLAN 20 的VRRP（SW1也是Master）
[SW1] interface Vlanif 20
[SW1-Vlanif20] vrrp vrid 1 virtual-ip 192.168.20.254
[SW1-Vlanif20] vrrp vrid 1 priority 120
[SW1-Vlanif20] vrrp vrid 1 preempt-mode timer delay 20

# VLAN 30 的VRRP（SW1作为Backup，SW2是Master → 负载均衡）
[SW1] interface Vlanif 30
[SW1-Vlanif30] vrrp vrid 1 virtual-ip 192.168.30.254
[SW1-Vlanif30] vrrp vrid 1 priority 100
# 默认优先级，低于SW2的120

# VLAN 40 的VRRP（SW1作为Backup）
[SW1] interface Vlanif 40
[SW1-Vlanif40] vrrp vrid 1 virtual-ip 192.168.40.254
[SW1-Vlanif40] vrrp vrid 1 priority 100
```

```bash
# ========= SW2（与SW1相反的角色）=========

# VLAN 10（SW2是Backup）
[SW2] interface Vlanif 10
[SW2-Vlanif10] vrrp vrid 1 virtual-ip 192.168.10.254
[SW2-Vlanif10] vrrp vrid 1 priority 100

# VLAN 20（SW2是Backup）
[SW2] interface Vlanif 20
[SW2-Vlanif20] vrrp vrid 1 virtual-ip 192.168.20.254
[SW2-Vlanif20] vrrp vrid 1 priority 100

# VLAN 30（SW2是Master）
[SW2] interface Vlanif 30
[SW2-Vlanif30] vrrp vrid 1 virtual-ip 192.168.30.254
[SW2-Vlanif30] vrrp vrid 1 priority 120
[SW2-Vlanif30] vrrp vrid 1 preempt-mode timer delay 20

# VLAN 40（SW2是Master）
[SW2] interface Vlanif 40
[SW2-Vlanif40] vrrp vrid 1 virtual-ip 192.168.40.254
[SW2-Vlanif40] vrrp vrid 1 priority 120
[SW2-Vlanif40] vrrp vrid 1 preempt-mode timer delay 20
```

> 💡 **设计智慧**：SW1当VLAN 10/20的Master，SW2当VLAN 30/40的Master。两台设备都在干活，不是简单的"一主一备"浪费资源。这叫**VRRP负载分担**。

# 阶段四：OSPF —— 让路由器自动学习路由

> 🔗 动态路由协议的核心区别与路由原理见 [[网络/TCP-IP详解/路由与交换的核心原理及区别]]

## 4.1 底层原理：OSPF是怎么工作的？

```
静态路由的问题：
  如果网络有50个网段，你需要在每个路由器上手动写50条路由
  如果链路断了，静态路由不会自动切换（除非配浮动路由）

OSPF（Open Shortest Path First）的解决思路：

🧠 核心思想：每个路由器都画出整个网络的"地图"，然后自己算最短路径

工作过程：
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│ 1️⃣ 邻居发现（Hello协议）                                   │
│    路由器向组播地址 224.0.0.5 发送Hello包                   │
│    "我是路由器A，Router-ID是1.1.1.1，谁在？"               │
│    邻居收到后回复Hello → 建立邻居关系                       │
│                                                             │
│ 2️⃣ 数据库同步（LSA交换）                                   │
│    路由器之间交换"链路状态通告"（LSA）                      │
│    每个LSA描述："我连接了哪些网段，代价是多少"              │
│    最终所有路由器都有完整的 LSDB（链路状态数据库）          │
│                                                             │
│ 3️⃣ SPF计算（Dijkstra算法）                                 │
│    每个路由器以自己为根，用Dijkstra算法算出到所有目的地的    │
│    最短路径树 → 生成路由表                                  │
│                                                             │
│ 4️⃣ 快速收敛                                               │
│    链路变化 → 只发送更新的LSA → 重新计算 → 秒级收敛        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### OSPF的"代价"（Cost）

```
OSPF用"代价"来衡量路径优劣，代价越小路径越好

默认Cost = 参考带宽 / 接口带宽
参考带宽默认 = 100Mbps

  100M以太网：Cost = 100/100 = 1
  1G以太网：  Cost = 100/1000 = 1（取整，所以千兆也是1，需要手动调整）
  10G以太网： Cost = 100/10000 = 1（同样需要调整）

建议：修改参考带宽
  [SW1-ospf-1] bandwidth-reference 100000
  这样千兆=100，万兆=10，更合理
```

# 阶段五：BGP —— 互联网的"外交官"协议

## 5.1 底层原理：为什么需要BGP？

```
OSPF的问题：
  OSPF适合"公司内部"——它追求的是"最快路径"
  但互联网有几十万条路由，OSPF扛不住
  而且互联网选路不光看"快"，还要看"策略"
  
  例如：我们公司有两条互联网线路
    电信：便宜但慢
    联通：贵但快
  我们希望：普通上网走电信，视频会议走联通
  
  OSPF做不到这种"策略选路"，BGP可以！

BGP（Border Gateway Protocol）的核心特点（也可见 [[网络/学习笔记/秦的网络]] 中的网络协议分层总结）：

┌─────────────────────────────────────────────────┐
│ 1. 路径矢量协议（不是距离矢量，也不是链路状态） │
│    记录完整路径：AS100 → AS200 → AS300          │
│    天然防环路：如果看到自己的AS号在路径中→丢弃  │
│                                                 │
│ 2. 基于TCP（端口179）                           │
│    不需要像OSPF那样自己实现可靠传输             │
│    直接用TCP的可靠性                             │
│                                                 │
│ 3. 策略控制极强                                  │
│    可以基于各种属性来控制选路                    │
│    Local_Pref、MED、AS_Path等                   │
│                                                 │
│ 4. 不追求"最快"，追求"最可控"                  │
│                                                 │
└─────────────────────────────────────────────────┘
```

### 关键概念：AS（自治系统）

```
AS（Autonomous System）= 一个独立管理的网络区域

  AS 100（星辰科技）          AS 65001（电信ISP）
  ┌──────────────┐           ┌──────────────┐
  │ AR1 ─────────┼───BGP─────┼── ISP路由器   │
  │ 内部用OSPF   │           │              │
  │ BGP在边界    │           │              │
  └──────────────┘           └──────────────┘

  BGP对等体之间交换路由：
  AR1告诉ISP："我能到达 192.168.0.0/16"
  ISP告诉AR1："我能到达 0.0.0.0/0（整个互联网）"

BGP的两种类型：
  EBGP（External BGP）：不同AS之间的BGP
  IBGP（Internal BGP）：同一AS内部的BGP
```

## 5.2 配置BGP

```bash
# ========= AR1 配置EBGP（与ISP对接）=========
[AR1] bgp 100
```

# 阶段七：MSTP + Eth-Trunk —— 打造"打不死"的核心骨干

## 7.1 底层原理：为什么需要这两个技术配合？

### 痛点分析

```
当前拓扑的致命缺陷：

SW3 ──── 单根千兆线 ──── SW1
         ↑
    如果这根线断了，A楼1层全部断网！
    
即使我们加一根线做备份：
SW3 ════ 线1 ════ SW1
      ════ 线2 ════ 
      
新问题来了：二层交换机会"泛洪广播帧"
如果两条线都通，广播帧会在 SW3↔SW1 之间无限循环！
→ 广播风暴 → 交换机CPU 100% → 全网瘫痪（比断线还惨）
```

### 解决方案组合拳

```
Eth-Trunk（链路聚合）：把多条物理线"捆"成一条逻辑线
  ✅ 带宽翻倍（2条1G = 2G）
  ✅ 线路冗余（断1条还有另1条）
  ✅ 对上层协议透明（STP只看到一条逻辑链路）

MSTP（多生成树协议）：在Eth-Trunk基础上防止环路
  ✅ 阻塞冗余路径，消除环路
  ✅ 不同VLAN走不同路径（负载分担）
  ✅ 链路故障时秒级切换备用路径
  
两者关系：
  先配 Eth-Trunk（把线捆起来）
  再配 MSTP（在逻辑链路上防环）
  ⚠️ 顺序不能反！否则STP可能错误阻塞物理口
```

## 7.2 Eth-Trunk 底层原理

```
Eth-Trunk 的工作模式：

┌─────────────────────────────────────────────────────┐
│  手工负载分担模式（推荐入门使用）                      │
│                                                      │
│  流量如何分配到各成员链路？                            │
│  → 基于"流"进行哈希分配                              │
│  → 同一条流（相同源MAC+目的MAC+源IP+目的IP）          │
│    始终走同一条物理链路                                │
│  → 不同的流可能走不同链路                              │
│                                                      │
│  为什么同一条流不走多条线？                            │
│  → 防止数据包乱序！                                   │
│  → TCP对乱序极其敏感，乱序=重传=性能暴跌              │
│                                                      │
│  LACP模式（生产环境推荐）                             │
│  → 两端通过LACPDU协商，自动检测链路故障               │
│  → 一端配置错误不会导致黑洞                           │
└─────────────────────────────────────────────────────┘
```

## 7.3 MSTP 底层原理

```
STP的演进史（理解这个才知道为什么要用MSTP）：

STP（802.1D）：所有VLAN共用一棵树
  → VLAN 10和VLAN 20都走同一条路径
  → 另一条路径完全闲置浪费
  
RSTP（802.1w）：快速收敛（从30秒→秒级）
  → 但仍然是所有VLAN共用一棵树
  
MSTP（802.1s）：多实例生成树
  → 把VLAN分组，每组映射到一个"实例"（Instance）
  → Instance 1: VLAN 10,20 → 走左边路径（Instance 0 是默认 IST，承载未映射的 VLAN）
  → Instance 2: VLAN 30,40 → 走右边路径
  → 既防环，又负载均衡！✅

MSTP关键概念：
┌──────────────────────────────────────────┐
│  MST域（Region）                          │
│  = 一组运行相同MSTP配置的交换机            │
│  三要素必须完全一致才能成为同一个域：       │
│    ① 域名（Region Name）                  │
│    ② 修订级别（Revision Level）           │
│    ③ VLAN-实例映射表                      │
│                                          │
│  Instance 0 = IST（内部生成树）           │
│  默认存在，承载未映射的VLAN                │
│  本案例中 VLAN 100/200 未显式映射，         │
│  它们属于 Instance 0，走默认生成树路径      │
└──────────────────────────────────────────┘
```

> 💡 **注意**：配置中只创建了 Instance 1（VLAN 10,20）和 Instance 2（VLAN 30,40）。VLAN 100 和 200 没有被显式映射，它们属于 **Instance 0（IST）**，走默认生成树路径。如果希望这些 VLAN 也参与负载分担，可以创建更多 Instance 并映射。

# 阶段八：DHCP + DHCP Snooping —— 自动化与安全并重

## 8.1 底层原理

### DHCP工作过程（DORA四步曲）

```
PC开机后如何自动获取IP？

┌──────────────────────────────────────────────────────────┐
│                                                          │
│  D - Discover（发现）                                     │
│    PC → 广播(255.255.255.255)                            │
│    "我是新来的，谁能给我IP？"                              │
│    源IP: 0.0.0.0  目标IP: 255.255.255.255                │
│                                                          │
│  O - Offer（提供）                                        │
│    DHCP Server → 单播/广播                                │
│    "我这有 192.168.10.100，租期8天，要不要？"             │
│                                                          │
│  R - Request（请求）                                      │
│    PC → 广播                                              │
│    "我要那个 .100！"                                      │
│    （广播是因为可能有多个Server回复，PC选一个）             │
│                                                          │
│  A - ACK（确认）                                          │
│    DHCP Server → 单播/广播                                │
│    "好的，.100给你了，网关.254，DNS 8.8.8.8"             │
│                                                          │
│  ✅ PC配置完成，开始通信                                   │
└──────────────────────────────────────────────────────────┘
```

### DHCP Snooping 解决什么问题？

```
攻击场景：有人在工位上私接了一个小路由器
  → 小路由器的DHCP Server也在工作
  → PC可能从小路由器获取到错误的IP和网关
  → 流量被劫持 / 无法上网 / IP冲突

DHCP Snooping 的原理：
  ┌─────────────────────────────────────────────┐
  │  把交换机端口分为两类：                        │
  │                                             │
  │  Trusted（信任口）：连接合法DHCP Server       │
  │    → 允许DHCP Reply（Offer/ACK）通过         │
  │                                             │
  │  Untrusted（非信任口）：连接用户PC            │
  │    → 只允许DHCP Request通过                  │
  │    → 丢弃DHCP Reply ← 非法服务器的回复被拦截！│
  │                                             │
  │  额外好处：生成绑定表                          │
  │  {MAC, IP, VLAN, Port}                       │
  │  → 后续可做DAI（动态ARP检测）防ARP欺骗        │
  └─────────────────────────────────────────────┘
```

# 阶段九：ACL + NAT —— 安全策略与互联网接入

## 9.1 ACL 底层原理

```
ACL（Access Control List）= 数据包的"安检门"

工作原理：
  ┌─────────────────────────────────────────┐
  │  逐条匹配，命中即停止（First Match）     │
  │                                         │
  │  Rule 5: permit tcp 192.168.10.0 → 30.0 │ ← 命中这条就放行
  │  Rule 10: deny tcp any → 192.168.30.0   │ ← 不会再检查
  │  Rule 15: permit ip any any             │
  │                                         │
  │  ⚠️ 隐含规则：末尾默认 deny any         │
  │  如果所有规则都没命中 → 丢弃！           │
  │  所以最后通常要加一条 permit ip any any  │
  └─────────────────────────────────────────┘

两种ACL类型：
  基本ACL（2000-2999）：只看源IP → 用于过滤"谁发的"
  高级ACL（3000-3999）：看源IP+目的IP+协议+端口 → 精确控制
  
应用方向：
  inbound  → 进入路由器/交换机之前检查
  outbound → 离开路由器/交换机之前检查
```

## 9.2 NAT 底层原理

```
为什么需要NAT？
  内网用的是私有IP（192.168.x.x），互联网不认！
  必须转换成公网IP才能上网

NAPT（最常用）：
  多个私网IP → 1个公网IP（靠端口号区分）
  
  内网PC1 (192.168.10.1:12345) → 访问百度
  AR1转换：(200.0.0.1:50001) → 百度
  
  内网PC2 (192.168.20.1:23456) → 访问淘宝  
  AR1转换：(200.0.0.1:50002) → 淘宝
  
  百度回复 → 200.0.0.1:50001 → AR1查NAT表 → 转给PC1
  淘宝回复 → 200.0.0.1:50002 → AR1查NAT表 → 转给PC2
  
  NAT表：
  ┌──────────────────────┬──────────────────────┐
  │ 内部地址              │ 外部地址              │
  │ 192.168.10.1:12345   │ 200.0.0.1:50001      │
  │ 192.168.20.1:23456   │ 200.0.0.1:50002      │
  └──────────────────────┴──────────────────────┘
```

## 9.3 配置ACL —— 实现安全策略

### 需求

```
安全策略：
1. 市场部(VLAN20) 禁止访问 财务部(VLAN30) 的任何服务
2. 研发部(VLAN10) 可以访问财务部，但只能访问HTTP(80)和HTTPS(443)
3. 所有部门都可以正常上互联网
4. 禁止任何人Telnet到核心交换机管理口（只允许SSH）
```

```bash
# ========= 在SW1上配置高级ACL =========

# ACL 3001：限制市场部访问财务部
[SW1] acl number 3001
[SW1-acl-adv-3001] rule 5 deny ip source 192.168.20.0 0.0.0.255 destination 192.168.30.0 0.0.0.255
# 拒绝市场部→财务部的所有IP流量
# 思科：access-list 101 deny ip 192.168.20.0 0.0.0.255 192.168.30.0 0.0.0.255

[SW1-acl-adv-3001] rule 10 permit ip
# 允许其他所有流量（别忘了隐含deny！）
[SW1-acl-adv-3001] quit

# ACL 3002：限制研发部访问财务部（只允许Web）
[SW1] acl number 3002
[SW1-acl-adv-3002] rule 5 permit tcp source 192.168.10.0 0.0.0.255 destination 192.168.30.0 0.0.0.255 destination-port eq 80
[SW1-acl-adv-3002] rule 10 permit tcp source 192.168.10.0 0.0.0.255 destination 192.168.30.0 0.0.0.255 destination-port eq 443
[SW1-acl-adv-3002] rule 15 deny ip source 192.168.10.0 0.0.0.255 destination 192.168.30.0 0.0.0.255
# 明确拒绝研发部→财务部的其他流量
[SW1-acl-adv-3002] rule 20 permit ip
[SW1-acl-adv-3002] quit

# 应用ACL到VLANIF接口（inbound方向）
[SW1] interface Vlanif 20
[SW1-Vlanif20] traffic-filter inbound acl 3001
# 在市场部网关的入方向过滤
# 思科：ip access-group 101 in

[SW1] interface Vlanif 10
[SW1-Vlanif10] traffic-filter inbound acl 3002
```

### 管理平面ACL（保护设备自身）

```bash
# ACL 3099：只允许特定网段SSH管理
[SW1] acl number 3099
[SW1-acl-adv-3099] rule 5 permit tcp source 192.168.10.0 0.0.0.255 destination-port eq 22
[SW1-acl-adv-3099] rule 10 deny tcp destination-port eq 23
# 拒绝所有Telnet
[SW1-acl-adv-3099] rule 15 permit ip
[SW1-acl-adv-3099] quit

# 配置 SSH 服务端（必须先配，否则 protocol inbound ssh 无法生效）
[SW1] rsa local-key-pair create
# 生成 RSA 密钥对（SSH 认证基础）
[SW1] ssh user admin
[SW1] ssh user admin authentication-type password
[SW1] ssh user admin service-type stelnet

# 配置 VTY 认证方式
[SW1] aaa
[SW1-aaa] local-user admin password cipher Admin@123
[SW1-aaa] local-user admin privilege level 15
[SW1-aaa] local-user admin service-type ssh
[SW1-aaa] quit

# 应用到VTY（远程登录）线路
[SW1] user-interface vty 0 4
[SW1-ui-vty0-4] authentication-mode aaa
[SW1-ui-vty0-4] acl 3099 inbound
[SW1-ui-vty0-4] protocol inbound ssh
# 只允许SSH协议（禁止Telnet）
[SW1-ui-vty0-4] quit
```

## 9.4 配置NAT（在AR1出口路由器上）

```bash
# ========= AR1 配置Easy IP（NAPT）=========

# 定义哪些内网地址可以做NAT
[AR1] acl number 2000
[AR1-acl-basic-2000] rule 5 permit source 192.168.0.0 0.0.255.255
# 匹配所有192.168.x.x的内网地址
[AR1-acl-basic-2000] quit

# 在出接口上配置NAT
[AR1] interface GigabitEthernet 0/0/1
# 这是连接ISP的公网接口
[AR1-GigabitEthernet0/0/1] nat outbound 2000
# 将ACL 2000匹配的流量，用此接口的IP做NAPT
# 思科：ip nat inside source list 1 interface GigabitEthernet0/1 overload

[AR1-GigabitEthernet0/0/1] quit

# 标记内外网口（部分版本需要）
[AR1] interface GigabitEthernet 0/0/0
[AR1-GigabitEthernet0/0/0] nat static enable
# 内网口
```

### 验证ACL和NAT

```bash
# 测试ACL
# 在市场部PC2上：
PC2> ping 192.168.30.1    # ❌ 应该不通（被ACL 3001拒绝）
PC2> ping 8.8.8.8         # ✅ 应该通（上互联网不受影响）

# 在研发部PC1上：
PC1> telnet 192.168.30.1  # ❌ 应该不通
PC1> curl 192.168.30.1    # ✅ HTTP应该通

# 查看ACL命中计数（确认规则是否生效）
[SW1] display acl 3001
# Rule 5: matched 15 packets ← 说明确实有流量被拒绝

# 查看NAT会话表
[AR1] display nat session all
# 内部地址           外部地址           协议
# 192.168.10.1:1234  200.0.0.1:5001    ICMP
# 192.168.20.1:5678  200.0.0.1:5002    TCP
```

# 阶段十：综合排错实战 —— 像老工程师一样思考

## 10.1 排错方法论（不是命令，是思维）

```
🧠 核心原则：分层排查 + 二分法定位

                    ┌─────────────┐
                    │  应用层问题？ │ ← ping通了但网页打不开
                    ├─────────────┤
                    │  路由/NAT？  │ ← ping不通外网但能ping网关
                    ├─────────────┤
                    │  三层连通性？ │ ← ping不通网关
                    ├─────────────┤
                    │  二层/VLAN？ │ ← 同VLAN ping不通
                    ├─────────────┤
                    │  物理层？    │ ← 灯都不亮
                    └─────────────┘

从下往上排查，每一层确认OK再往上一层
```

## 10.2 经典故障场景演练

### 场景1：PC1无法获取DHCP地址

```bash
# Step 1: 检查物理层
[SW3] display interface GigabitEthernet 0/0/1
# 看 Line protocol 是否 UP

# Step 2: 检查VLAN配置
[SW3] display port vlan
# 确认GE0/0/1确实在VLAN 10

# Step 3: 检查DHCP Snooping是否误拦截
[SW3] display dhcp snooping statistics
# 看是否有大量dropped的DHCP Reply
# 如果有 → 检查上行Trunk口是否配了trusted

# Step 4: 检查DHCP Server
[SW1] display ip pool name VLAN10-Pool
# 地址池是否耗尽？
# 网关配置是否正确？

# Step 5: 抓包验证（终极手段）
# 在eNSP中对PC1的链路右键→Start Capture
# 过滤 bootp，看DORA四步走到哪一步停了
```

### 场景2：VLAN间能通但上不了网

```bash
# Step 1: 确认网关可达
PC1> ping 192.168.10.254  # ✅ 通

# Step 2: 确认核心到出口路由
[SW1] display ip routing-table 0.0.0.0
# 有没有默认路由？下一跳是谁？

# Step 3: 确认AR1的OSPF邻居
[AR1] display ospf peer brief
# 与SW1/SW2的邻居是否Full？

# Step 4: 确认NAT
[AR1] display nat session all
# PC1的流量有没有出现在NAT表中？
# 没有 → 检查ACL 2000是否匹配了PC1的网段
# 有但回不来 → 检查ISP侧路由

# Step 5: 确认BGP
[AR1] display bgp peer
# 状态是否Established？
```

### 场景3：VRRP切换后部分VLAN不通

```bash
# 最常见原因：SW2上没有对应VLAN的VLANIF或OSPF没宣告

# Step 1: 检查SW2的VRRP状态
[SW2] display vrrp brief
# 确认接管成功

# Step 2: 检查SW2的路由表
[SW2] display ip routing-table
# 有没有到所有VLAN的直连路由？
# 有没有到出口的默认路由？

# Step 3: 检查Trunk允许的VLAN
[SW2] display port vlan
# 确认所有VLAN都在Trunk允许列表中
# ⚠️ 这是最常见的遗漏！加了新VLAN忘了改Trunk
```
