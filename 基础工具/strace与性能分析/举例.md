## 场景 1：程序启动闪退 / 动态库缺失

### 问题描述

你编译了一个 C 程序 `myapp`，跑起来直接退出，没有任何日志，连 "Segmentation fault" 都没有。终端干干净净。

```
$ ./myapp
$ echo $?
1
```

进程直接退出，返回码 1，没有任何输出。

### strace 命令

```bash
strace -o /tmp/strace.log ./myapp
```

为什么不加 `-e` 过滤？因为此时你不知道问题出在哪，需要完整的启动流程。

### 输出分析

打开 `/tmp/strace.log`：

```
execve("./myapp", ["./myapp"], [/* 48 vars */]) = 0
brk(NULL)                               = 0x55555556a000
mmap(NULL, 8192, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7ffff7fce000
...
openat(AT_FDCWD, "libfoo.so", O_RDONLY|O_CLOEXEC) = -1 ENOENT (No such file or directory)
openat(AT_FDCWD, "/usr/lib/libfoo.so", O_RDONLY|O_CLOEXEC) = -1 ENOENT
openat(AT_FDCWD, "/usr/local/lib/libfoo.so", O_RDONLY|O_CLOEXEC) = -1 ENOENT
openat(AT_FDCWD, "/lib/x86_64-linux-gnu/libfoo.so", O_RDONLY|O_CLOEXEC) = -1 ENOENT
write(2, "error: cannot open libfoo.so\n", 30) = 30
exit_group(1)                           = ?
+++ exited with 1 +++
```

关键行：

```
openat(..., "libfoo.so", ...) = -1 ENOENT
write(2, "error: cannot open libfoo.so\n", 30) = 30
exit_group(1)
```

程序试图加载 `libfoo.so`，在所有标准路径都没找到，最后把错误信息**写到了 stderr（fd 2）**而不是 stdout。你直接在终端跑的时候没看到，因为它只显示 stdout。

### 根因与方案

**根因**：动态库 `libfoo.so` 不在标准搜索路径中，也没有被链接到可执行文件。

**方案**：

```bash
# 方案 A：安装缺失的库
sudo apt-get install libfoo-dev    # Debian/Ubuntu
sudo yum install libfoo-devel      # RHEL/CentOS

# 方案 B：指定库路径
LD_LIBRARY_PATH=/path/to/lib ./myapp

# 方案 C：更新 ld 缓存
sudo ldconfig /path/to/lib

# 方案 D：编译时静态链接
gcc -static -o myapp myapp.c -lfoo
```

## 场景 2：网络服务端口绑定权限

### 问题描述

启动 Nginx 时报错：

```
$ nginx
nginx: [emerg] bind() to 0.0.0.0:80 failed (13: Permission denied)
```

但 `nginx.conf` 看起来是对的，端口 80 也没被占。

### strace 命令

```bash
strace -f -e trace=network,bind -s 256 -o /tmp/nginx.strace nginx
```

这里 `-f` 跟踪子进程（nginx 会 fork worker），`-e trace=network,bind` 只看网络相关调用。

### 输出分析

```
[pid  1234] socket(AF_INET, SOCK_STREAM, IPPROTO_IP) = 3
[pid  1234] setsockopt(3, SOL_SOCKET, SO_REUSEADDR, [1], 4) = 0
[pid  1234] bind(3, {sa_family=AF_INET, sin_port=htons(80), sin_addr=inet_addr("0.0.0.0")}, 16) = -1 EACCES (Permission denied)
[pid  1234] close(3)                    = 0
[pid  1234] write(2, "nginx: [emerg] bind() to 0.0.0.", ...) = 42
```

`bind()` 返回 `EACCES`。但 `lsof -i :80` 显示端口没有被占用。问题出在哪？

### 根因与方案

**根因**：Linux 上，绑定 1024 以下的端口需要 root 权限或 `CAP_NET_BIND_SERVICE` 能力。当前用户是普通用户，没有权限。

**验证**：

```bash
$ whoami
alice
$ capsh --print | grep net_bind_service  # 没有输出，说明没有该能力
```

**方案**：

```bash
# 方案 A：用 root 启动
sudo nginx

# 方案 B：使用 1024 以上端口（如 8080），再用 iptables 转发
# 修改 nginx.conf: listen 8080;
# iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-port 8080

# 方案 C：赋予能力位（不需要 root，推荐）
sudo setcap 'cap_net_bind_service=+ep' /usr/sbin/nginx
# 之后普通用户就能绑定 80 端口

# 方案 D：使用 authbind
sudo apt-get install authbind
authbind --deep nginx
```

## 场景 3：文件描述符泄漏

### 问题描述

服务运行一段时间后开始报错：

```
Exception in thread "main": too many open files
```

或系统日志：

```
kernel: VFS: file-max limit <N> reached
```

`lsof -p <PID>` 看到成千上万个打开的 fd。但代码里明明有 `close()`。

### strace 命令

先确认 fd 是持续增长还是稳定：

```bash
# 1. 持续观察 fd 数量
watch -n 1 "ls /proc/<PID>/fd | wc -l"

# 2. 用 strace 只关注 open/close/create 类调用
strace -e trace=open,openat,creat,close,dup,dup2 \
       -o /tmp/fdleak.log -p <PID>
```

运行 5~10 秒后 Ctrl+C 停止。

### 输出分析

```
openat(AT_FDCWD, "/var/log/app.log", O_WRONLY|O_APPEND|O_CREAT, 0644) = 10
write(10, "INFO: request processed\n", 24) = 24
# ... 很多正常 IO ...
openat(AT_FDCWD, "/var/data/session_abc123.tmp", O_RDWR|O_CREAT, 0600) = 11
# ... 处理 session ...
close(11)      ← 等等，这里也 close 了？
# ...
openat(AT_FDCWD, "/var/data/session_def456.tmp", O_RDWR|O_CREAT, 0600) = 12
# ... 处理 session ...
# 没 close(12)
openat(AT_FDCWD, "/var/data/session_ghi789.tmp", O_RDWR|O_CREAT, 0600) = 13
```

每次创建 session 临时文件时打开了一个新 fd，但某些路径下忘了 `close()`。这个泄漏点不在每次必走的路径上，而是只在特定条件下触发（比如某个异常分支）。

### 根因与方案

**根因**：代码中有条件分支忘记关闭文件描述符。

**定位方法**：用 `lsof` 看泄漏的 fd 对应什么文件：

```bash
# 看到大量打开的临时文件
lsof -p <PID> | grep session
```

然后去代码里搜索 session 文件的 open/create 操作，检查所有 return、throw、goto 分支是否都有关闭操作。

**方案**：

```bash
# 临时应急：增大 fd 限制
ulimit -n 65536
# 或修改 /etc/security/limits.conf

# 长期方案：修复代码
# - 使用 RAII（C++）/ try-with-resources（Java）/ with 语句（Python）
# - 在 finally / defer 中确保关闭
# - 使用 fd 泄漏检测工具：valgrind --track-fds=yes ./myapp
```

**Python 示例**：

```python
# 错的
f = open("/tmp/data.txt", "r")
data = f.read()
if not data:
    return   # 忘了 f.close()
process(data)

# 对的
with open("/tmp/data.txt", "r") as f:
    data = f.read()
    if not data:
        return
    process(data)
```

**C 示例**：

```c
// 错的
int fd = open("/tmp/data", O_RDONLY);
char *buf = malloc(4096);
if (!buf) return -1;  // 忘了 close(fd)
read(fd, buf, 4096);
// ...

// 对的
int fd = open("/tmp/data", O_RDONLY);
char *buf = malloc(4096);
if (!buf) { close(fd); return -1; }
// ...
close(fd);
```

## 场景 4：进程卡死 / 僵尸进程

### 问题描述

你的服务进程还在，但既不响应请求也不退出。`kill -9` 都杀不死。或者变成了僵尸进程（Z 状态）。

### 分析步骤

先看进程状态：

```bash
ps aux | grep myapp
# 状态列：D (不可中断睡眠) / Z (僵尸) / S (可中断睡眠)
```

### strace 命令

```bash
# 对 D 状态进程用 strace
strace -p <PID>
```

如果进程卡在 D 状态（`TASK_UNINTERRUPTIBLE`），strace 也可能卡住。这时可以看 `/proc` 获取最后执行的 syscall：

```bash
# 查看进程最后执行的系统调用
cat /proc/<PID>/syscall
# 输出示例：0 0x7f... 0x7f... 0x0 0x0 0x0 0x0 0x0 0x7f...
#          ^ syscall 号

# 对照 /usr/include/asm/unistd_64.h 查看编号含义
# 或使用
cat /proc/<PID>/wchan
# 输出示例：do_block_io_op  ← 卡在 IO 阻塞
```

### 输出分析

#### 案例 A：卡在 IO（D 状态）

```
# cat /proc/1234/syscall
2 0x7f... 0x7f... 0x20000 0x0 0x0 0x0 0x0 0x0 0x7f...
```

syscall 号 2 是 `open`。进程卡在打开文件的操作上，底层可能是 NFS 挂掉或者磁盘故障。

#### 案例 B：僵尸进程

```bash
ps aux | grep defunct
# 输出中有 [myapp] <defunct>
# 状态 Z
```

僵尸进程已经死亡但父进程没有 `wait()` 回收。strace 附不上去，但可以跟踪父进程：

```bash
strace -e trace=wait4,waitid -p <父进程PID>
```

输出：

```
wait4(-1, 0x7fff..., WNOHANG, NULL) = 0  ← 非阻塞调用，有子进程但没处理
wait4(-1, 0x7fff..., WNOHANG, NULL) = 0
wait4(-1, 0x7fff..., WNOHANG, NULL) = 0
```

父进程使用 `WNOHANG` 非阻塞检查子进程，但从不调用阻塞的 `wait()` 来真正回收。

### 根因与方案

**D 状态方案**：

```bash
# 1. 等 IO 完成（大部分 D 状态是短暂的）
# 2. 检查 NFS 挂载是否正常
mount | grep nfs
showmount -e <nfs_server>
# 3. 检查磁盘健康
smartctl -a /dev/sda
dmesg | tail
# 4. 恢复 NFS：重启 nfs 服务或 remount
# 5. 如果实在不行，重启机器
```

**僵尸进程方案**：

```bash
# 1. 杀死父进程，僵尸被 init 回收
kill -9 <父进程PID>

# 2. 如果不想杀父进程，发送 SIGCHLD 触发父进程 wait
# （取决于父进程实现，不一定有效）
kill -CHLD <父进程PID>

# 3. 长期修复：父进程应正确调用 wait() / waitpid()
```

## 场景 5：权限问题（EACCES / EPERM）

### 问题描述

程序读取某个文件时报错，但 `ls -l` 看起来权限是够的：

```bash
$ ./myapp /etc/secret/config
Error: cannot read config
$ ls -l /etc/secret/config
-rw-r--r-- 1 root root 1024 Apr 1 12:00 /etc/secret/config
```

文件权限是 644，任何用户都能读，为什么程序读不了？

### strace 命令

```bash
strace -e trace=openat,open,stat,faccessat -s 256 ./myapp /etc/secret/config
```

### 输出分析

```
openat(AT_FDCWD, "/etc/secret/config", O_RDONLY) = -1 EACCES (Permission denied)
```

但文件明明是 644。继续看 strace 输出前面的部分：

```
openat(AT_FDCWD, "/etc/secret", O_RDONLY|O_DIRECTORY) = -1 EACCES (Permission denied)
```

问题不在文件，而在**目录**：

```bash
$ ls -ld /etc/secret
drwx------ 2 root root 4096 Apr 1 12:00 /etc/secret
```

目录 `/etc/secret` 权限是 700，只有 root 能进入（需要 execute 权限）。当前用户没有目录的 x 权限，自然无法访问里面的文件，即使文件本身是 644。

### 根因与方案

**根因**：目录缺少 execute 权限。Unix 权限模型中，对目录的 x 权限（search/traverse）决定了能否进入该目录。

**方案**：

```bash
# 方案 A：给目录加 x 权限
sudo chmod +x /etc/secret

# 方案 B：改变文件位置
sudo mv /etc/secret/config /etc/config
sudo chmod 644 /etc/config

# 方案 C：用 sudo 运行程序
sudo ./myapp /etc/secret/config

# 方案 D：将用户加入特定组
sudo chown root:appgroup /etc/secret
sudo chmod 750 /etc/secret   # 目录属于 root:appgroup，组用户可进入
sudo usermod -aG appgroup $USER
```

### 另一个权限变体：EPERM

```
ioctl(3, TIOCSTI, ...) = -1 EPERM (Operation not permitted)
```

`EPERM` 通常出现在以下场景：

- 试图向不属于自己的进程发信号
- 某些特权 `ioctl` 操作
- `chmod` / `chown` 文件但不在文件所有者
- 加载内核模块

## 场景 6：配置文件读取错误路径

### 问题描述

改了 `/etc/myapp/config.yml`，重启服务，新配置没生效。服务读的好像是旧文件或者别的路径。

### strace 命令

```bash
# 只看文件打开操作
strace -e trace=open,openat,stat -s 256 -o /tmp/config_trace.log myapp
```

### 输出分析

```
openat(AT_FDCWD, "/etc/myapp/config.yml", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/etc/myapp/config.yaml", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/etc/myapp/config.json", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/etc/myapp/default.yml", O_RDONLY) = 3
```

关键发现：

1. 程序尝试了 `.yml`、`.yaml`、`.json` 三种扩展名
2. 三种都不存在
3. 最后加载了 `/etc/myapp/default.yml`

**但你改的是 `/etc/myapp/config.yml`！**

```bash
$ ls -la /etc/myapp/
total 24
drwxr-xr-x  2 root root 4096 Apr 1 12:00 .
-rw-r--r--  1 root root 2048 Apr 1 11:50 config.yml
-rw-r--r--  1 root root 2048 Mar 1 09:00 default.yml
```

`config.yml` 存在。但为什么 strace 显示 `ENOENT`？

再看细节：

```
openat(AT_FDCWD, "/etc/myapp/config.yml", O_RDONLY) = -1 EACCES (Permission denied)
```

等等，第一遍是 EACCES 不是 ENOENT。但之前 strace 输出是 ENOENT？再仔细看：

```
openat(AT_FDCWD, "/etc/myapp/config.yml", O_RDONLY) = -1 EACCES
openat(AT_FDCWD, "/etc/myapp/config.yaml", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/etc/myapp/config.json", O_RDONLY) = -1 ENOENT
openat(AT_FDCWD, "/etc/myapp/default.yml", O_RDONLY) = 3
```

`config.yml` 实际上是**权限错误**（EACCES），不是不存在！等程序尝试 `.yaml` 和 `.json` 发现确实不存在后，回退到了 `default.yml`。

### 根因与方案

**根因**：`/etc/myapp/config.yml` 文件权限被错误设置（可能改配置时没注意 umask），当前用户读不了。程序没有针对 EACCES 特殊处理，直接认为"不能读"然后跳到下一个候选文件。

**验证**：

```bash
ls -l /etc/myapp/config.yml
# 可能是：------- 1 root root 2048 ...  ← 谁也读不了
```

**方案**：

```bash
# 修权限
sudo chmod 644 /etc/myapp/config.yml

# 或确认文件所有者
sudo chown myapp:myapp /etc/myapp/config.yml
```

## 场景 7：信号处理异常

### 场景 7A：段错误（SIGSEGV）

#### 问题描述

程序突然崩溃，`dmesg` 可能有也可能没有信息：

```bash
$ ./myapp
Segmentation fault (core dumped)
```

#### strace 命令

```bash
strace -o /tmp/sigsegv.log ./myapp
```

#### 输出分析

```
mmap(NULL, 4096, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0x7f...
...
--- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=0x0} ---
+++ killed by SIGSEGV (core dumped) +++
```

关键信息：

- `si_addr=0x0`：试图访问地址 0（空指针解引用）
- `si_code=SEGV_MAPERR`：地址没有映射到任何内存区域
- 信号在某个 syscall 返回**之后**触发的，说明在用户态代码中崩溃

如果 `si_addr` 是一个非零地址（如 `0x7f12345678`），可能是**野指针**或**释放后使用**（use-after-free）。

如果 `si_code=SEGV_ACCERR`，说明访问了**已有映射但无权限**的内存（比如试图写只读页）。

### 场景 7B：SIGPIPE 导致进程退出

#### 问题描述

一个网络服务在压力测试下频繁断开连接。

#### strace 命令

```bash
strace -e trace=network,write,read -o /tmp/sigpipe.log -p <PID>
```

#### 输出分析

```
write(4, "HTTP/1.1 200 OK...", 1450) = -1 EPIPE (Broken pipe)
--- SIGPIPE {si_signo=SIGPIPE, si_pid=0, si_uid=0} ---
+++ killed by SIGPIPE +++
```

程序写 socket 时对端已经关闭连接，内核返回 `EPIPE` 并发送 `SIGPIPE` 信号。程序没有处理 `SIGPIPE`，默认行为是杀死进程。

#### 根因与方案

**根因**：客户端提前断开连接，服务端继续往 socket 写数据。

**方案**：

```bash
# 方案 A：忽略 SIGPIPE（网络服务常用）
# C 代码
signal(SIGPIPE, SIG_IGN);
# 或者用 sigaction

# 方案 B：使用 MSG_NOSIGNAL（Linux）或 SO_NOSIGPIPE（BSD）
# C 代码
send(fd, buf, len, MSG_NOSIGNAL);
# 这样 EPIPE 会正常返回，你可以在代码里优雅处理

# 方案 C：检查 write/send 的返回值
# 如果返回 -1 且 errno==EPIPE，不要继续写，关闭连接
```

### 场景 7C：进程收到 SIGTERM 不退出

#### 问题描述

```bash
kill <PID>  # 默认 SIGTERM
# 进程没反应
kill -9 <PID>
# 进程才死
```

#### strace 命令

```bash
# 先 kill，然后立刻
strace -p <PID>
```

#### 输出分析

```
restart_syscall(<... resuming interrupted call ...>) = 0
--- SIGTERM {si_signo=SIGTERM, si_pid=1, si_uid=0} ---
# strace 没有显示 kill/sigaction 处理，说明没有注册处理函数
```

进程没有为 `SIGTERM` 注册信号处理函数。默认行为是终止，但进程可能卡在**不可中断的睡眠**（D 状态），连信号都无法递送。查看 `/proc/<PID>/status`：

```bash
cat /proc/<PID>/status | grep -E "State|SigCgt"
# State:	D (disk sleep)
# SigCgt:	0000000000000000  ← 没有捕获任何信号
```

D 状态的进程连 SIGKILL 都杀不死。唯一办法是等 IO 完成，或重启机器。

## 场景 8：子进程跟踪（fork / exec 调试）

### 问题描述

一个父进程启动多个子进程做任务，某些子进程启动失败或异常退出，但父进程的日志太模糊，看不出是哪个子进程、哪里出问题。

### strace 命令

```bash
# 跟踪所有子进程，用不同文件保存
strace -ff -o /tmp/worker ./master_process
```

`-ff` 会让每个进程的输出分开：`/tmp/worker`（主进程）、`/tmp/worker.1234`（子进程1）、`/tmp/worker.1235`（子进程2）...

### 输出分析

主进程 `worker`：

```
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD) = 1234
clone(child_stack=NULL, flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD) = 1235
wait4(-1, [{WIFEXITED(s) && WEXITSTATUS(s) == 1}], 0, NULL) = 1234
wait4(-1,  [{WIFEXITED(s) && WEXITSTATUS(s) == 0}], 0, NULL) = 1235
```

主进程 `clone()` 了两次，得到子进程 1234 和 1235，然后 `wait4()` 等待子进程结束。1234 退出码 1（异常），1235 退出码 0（正常）。

查看子进程 1234 的输出 `worker.1234`：

```
execve("/usr/bin/worker_child", ["worker_child", "--input", "/tmp/data"], [/* ... */]) = 0
openat(AT_FDCWD, "/tmp/data", O_RDONLY) = -1 ENOENT (No such file or directory)
write(2, "Error: input file not found\n", 29) = 29
exit_group(1)
```

子进程 1234 要读 `/tmp/data`，但这个文件不存在。它把错误写到了 stderr，父进程没转发。

### 根因与方案

**根因**：子进程启动时需要的输入文件缺失。

**方案**：

```bash
# 1. 确保输入文件存在
touch /tmp/data

# 2. 或修改主进程，转发子进程的 stderr
# 3. 或让子进程通过父进程的日志系统写错误
```

**定位子进程的通用方法**：

```bash
# 用 grep 搜索所有子进程输出文件中的关键信息
grep -l "ENOENT\|EACCES\|signal\|killed" /tmp/worker.*

# 按 pid 排序查看各个进程的退出码
grep "exited with" /tmp/worker.*
```

## 场景 9：快速性能排查统计

### 问题描述

服务响应变慢，想快速排查是不是系统调用层面的问题。不确定是 IO 慢、锁竞争还是 CPU 密集型。

### strace 命令

```bash
# 附着运行中的进程，统计 10 秒
strace -c -p <PID>
# 等 10 秒然后 Ctrl+C
```

### 输出分析

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 58.23    0.583212         112       5200           epoll_wait
 20.11    0.201322           5      40212           writev
 12.45    0.124512           3      41000           readv
  5.21    0.052132          10       5200           accept4
  2.00    0.020010           2      10000           sendfile64
------ ----------- ----------- --------- --------- ----------------
100.00    1.005318                 101612         total
```

**解读**：

- `epoll_wait` 占 58% 时间，平均每次 112 微秒 → 在 etc 事件，实际大部分时间空闲
- `writev` / `readv` 各 4 万多次，每次 3~5 微秒 → 高吞吐正常 IO
- **没有异常点** → 瓶颈不在系统调用层，应该看 CPU 层面的分析

**异常示例**：

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 90.00    9.000000       90000        100           read
```

单次 read 平均 90 毫秒 → 磁盘或网络 IO 非常慢，需要排查存储或网络。

更详细的性能分析方法和高级技巧见《性能分析.md》。

## 常见 syscall 速查解释

调试过程中会频繁遇到以下系统调用。知道它们在做什么，能帮你更快读懂输出：

### 文件与 IO

| syscall | 含义 | 典型调试场景 |
|---------|------|-------------|
| `openat` / `open` | 打开文件或设备 | 配置文件、日志文件、设备驱动 |
| `read` | 从 fd 读数据 | 文件读取、socket 收数据 |
| `write` | 往 fd 写数据 | 文件写入、socket 发数据、日志输出 |
| `close` | 关闭 fd | FD 泄漏排查 |
| `stat` / `fstat` / `newfstatat` | 获取文件元信息 | 检查文件是否存在、权限、大小 |
| `lseek` | 移动文件读写指针 | 随机读写文件 |
| `mmap` | 内存映射文件或匿名内存 | 动态库加载、大文件映射、内存分配 |
| `brk` | 调整堆（heap）大小 | 小内存分配（malloc 内部使用） |
| `fcntl` | 操作 fd 的各种属性 | 设置非阻塞、FD_CLOEXEC、文件锁 |
| `ioctl` | 设备控制操作 | 终端、网络设备、硬件驱动 |
| `sendfile` | 零拷贝文件传输 | 静态文件服务效率分析 |
| `fallocate` | 预分配磁盘空间 | 文件预分配 |
| `fsync` / `fdatasync` | 刷盘确保数据落盘 | 写性能、数据可靠性分析 |
| `preadv` / `pwritev` | 向量化读写（指定偏移） | 高性能 IO 分析 |

### 网络

| syscall | 含义 | 典型调试场景 |
|---------|------|-------------|
| `socket` | 创建套接字 | 网络连接建立 |
| `bind` | 绑定地址和端口 | 端口冲突、权限问题 |
| `listen` | 开始监听 | 服务端启动 |
| `accept` / `accept4` | 接受连接 | 连接接入 |
| `connect` | 发起连接 | 客户端连接超时 |
| `sendto` / `sendmsg` | 发送数据 | 网络发送 |
| `recvfrom` / `recvmsg` | 接收数据 | 网络接收 |
| `setsockopt` | 设置 socket 选项 | SO_REUSEADDR、TCP_NODELAY 等 |
| `getsockopt` | 获取 socket 选项 | 获取错误状态 |
| `shutdown` | 关闭连接 | 半关闭 |
| `poll` / `select` | IO 多路复用（传统） | 事件循环、连接等待 |
| `epoll_create` / `epoll_ctl` / `epoll_wait` | 高效 IO 多路复用 | Nginx、Node.js、Redis 等高性能服务 |
| `splice` | 两个 fd 之间的零拷贝传输 | 高效数据转发 |

### 进程与信号

| syscall | 含义 | 典型调试场景 |
|---------|------|-------------|
| `fork` / `clone` | 创建进程/线程 | 进程/线程创建分析 |
| `execve` / `execveat` | 执行新程序 | 程序启动、shell 调试 |
| `exit` / `exit_group` | 退出 | 进程退出分析 |
| `wait4` / `waitid` | 等待子进程 | 子进程回收（僵尸进程） |
| `kill` / `tkill` | 发送信号 | 信号发送 |
| `sigaction` / `rt_sigaction` | 设置信号处理函数 | 信号处理注册 |
| `sigprocmask` | 阻塞/解除阻塞信号 | 信号屏蔽 |
| `nanosleep` | 高精度睡眠 | 定时器、延迟 |

### 锁与同步

| syscall | 含义 | 典型调试场景 |
|---------|------|-------------|
| `futex` | 用户态快速锁操作 | 锁竞争、线程阻塞 |
| `sched_yield` | 主动让出 CPU | 忙等（busy loop） |
| `sched_setaffinity` | 设置 CPU 亲和性 | CPU 绑定 |
| `flock` | 文件锁 | 文件互斥 |
| `semop` | 信号量操作 | 进程间同步 |

### 其他

| syscall | 含义 | 典型调试场景 |
|---------|------|-------------|
| `getpid` | 获取进程 ID | 进程标识 |
| `gettid` | 获取线程 ID | 线程标识 |
| `clock_gettime` | 获取时间 | 时间相关 |
| `prctl` | 进程控制操作 | 设置进程名、seccomp |
| `seccomp` | 安全计算模式 | 沙箱、安全限制 |
| `capget` / `capset` | 能力位操作 | 权限检查 |
| `mlock` / `mlockall` | 内存锁定（不许换出） | 实时应用 |
| `mprotect` | 修改内存页保护属性 | JIT 编译器 |
| `uname` | 获取系统信息 | 系统版本检查 |
| `sysinfo` | 获取系统统计 | 系统负载 |
