strace 做性能分析的核心是找到 **慢在哪**，然后对症下药。

---

## 1. 快速定位慢的系统调用：`-T`

```bash
strace -T curl https://example.com 2>&1 | head -20
```

```
connect(3, ...) = 0 <0.000035>         ← 3 微秒
connect(4, ...) = -1 EINPROGRESS <0.003261>
poll([{fd=4, events=POLLOUT}], 1, 30000) = 1 <210.543919>  ← 210 毫秒
write(4, "GET / HTTP/1.1...", 79) = 79 <0.000210>
read(4, "HTTP/1.1 200 OK...", 4096) = 1450 <0.000445>
```

一眼看出 `poll` 花了 **210ms** → 网络延迟（TCP 连接建立耗时）是瓶颈，不是代码逻辑问题。

---

## 2. 汇总统计模式：`-c`

最实用的性能分析方式：

```bash
$ strace -c -f -p $(pgrep nginx) &
$ sleep 10
$ kill %1
```

输出：
```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 58.23    0.583212         112       5200           epoll_wait
 20.11    0.201322           5      40212           writev
 12.45    0.124512           3      41000           readv
  5.21    0.052132          10       5200           accept4
  2.00    0.020010           2      10000           sendfile64
------ ----------- ----------- --------- --------- ----------------
100.00    1.005318                 101612         total
```

**解读**：
- `epoll_wait` 占 58% 但在等事件 → 实际空闲，**正常**
- `writev` + `readv` 各 4 万次，但每次只要 3~5 微秒 → **高吞吐 IO，正常**
- **没有某个异常耗时 syscall** → 瓶颈不在内核，可能在应用层（CPU 计算），该上 `perf` / `flamegraph`

反过来，如果看到：
```
 90%   read     每次 20000 微秒  只有 50 次调用
```
说明**磁盘或网络读取极慢**，单次 read 20ms。

## 3. 只看耗时操作：过滤

```bash
# 只看耗时超过 1ms 的 syscall
strace -T -e trace=all myapp 2>&1 | awk -F'[<>]' '$2+0 > 1 {print $0}'
```

或者用 `-e trace=` 缩小范围：

```bash
# 只看文件 IO 耗时（磁盘瓶颈）
strace -c -e trace=file myapp

# 只看网络相关（延迟/丢包）
strace -c -e trace=network,connect,sendto,recvfrom myapp

# 只看内存映射（mmap 太多可能内存碎片）
strace -c -e trace=mmap,brk,mprotect myapp
```

## 4. 时序分析：两次调用之间的时间

```bash
strace -tt -T myapp 2>&1 | grep -E "(openat|read|write)"
```

```
10:00:01.000123 openat(..., "config.json", ...) = 3 <0.000045>
10:00:01.000456 read(3, ..., 4096) = 4096 <0.000320>   ← config 花了 0.3ms
10:00:05.023456 openat(..., "bigfile.bin", ...) = 4 <0.000050>
10:00:05.452331 read(4, ..., 65536) = 65536 <0.428925> ← 429ms 读大文件
10:00:05.452335 read(4, ..., 65536) = 65536 <0.000002> ← 第二次被 cache 了
```

可见读 `bigfile.bin` 是瓶颈（可能没开 buffer 或局部分区差），第一次 429ms，第二次 2μs —— 说明 OS cache 生效了。

## 5. 实战范例：服务器 100% CPU 排查

```bash
# 找到高 CPU 进程
top -bn1 | head

# 附着 strace 统计
strace -c -p <PID>
```

输出：
```
 99%  sched_yield      每次 0ms   100万次/秒
```

进程疯狂调用 `sched_yield` 而不是阻塞 → **忙等（busy loop）**，比如无锁自旋或 `while (1)` 空转。

## 6. strace 的局限与互补工具

| 工具 | 定位 | 适合 |
|------|------|------|
| **strace** | 系统调用层 | IO 瓶颈、错误码、文件访问、网络延迟 |
| **perf** | CPU 指令级 | CPU 热点、cache miss、分支预测 |
| **perf top** | 实时热点函数 | 哪个函数消耗 CPU 最多 |
| **flamegraph** | 可视化 CPU 栈 | 一眼看出热点路径 |
| **ltrace** | 库调用层 | 库函数调用次数和耗时 |
| **iostat** | 磁盘 IO | 磁盘吞吐、队列深度、await |
| **tcpdump** | 网络包粒度 | 重传、延迟分布、握手细节 |

**典型分工**：
- strace 告诉你**程序在内核里做了什么**（open/read/write/poll）
- perf 告诉你**程序在用户态代码的哪里慢**（哪个函数、哪一行）
- 两者互补，覆盖从内核到用户态的全链路

---

## 总结：strace 性能分析的判断路径

```
高 CPU？
├── strace -c → 大量 sched_yield → 用户态忙等
├── strace -c → 大量 read/write → IO 事件驱动正常
└── strace -c → 调用很少 → CPU 在用户态算 → 上 perf

慢响应？
├── strace -T → connect/poll 几百毫秒 → 网络延迟
├── strace -T → read 几十毫秒 → 磁盘慢
└── strace -T → 都是微秒级 → 瓶颈不在 syscall
```
