## 1. 快速定位慢调用：-T

`-T` 在每行末尾打印该系统调用的耗时（微秒）。适合对单次请求做精确定位。

```bash
strace -T curl https://example.com 2>&1 | head -20
```

输出：

```
connect(3, ...) = 0 <0.000035>         ← 3 微秒
connect(4, ...) = -1 EINPROGRESS <0.003261>
poll([{fd=4, events=POLLOUT}], 1, 30000) = 1 <210.543919>  ← 210 毫秒
write(4, "GET / HTTP/1.1...", 79) = 79 <0.000210>
read(4, "HTTP/1.1 200 OK...", 4096) = 1450 <0.000445>
```

一眼看出 `poll` 花了 **210ms**。这是等待 TCP 连接建立完成的时间。

**判断标准**：

- `<0.1ms`：正常（微秒级，基本上是内存操作）
- `0.1ms ~ 1ms`：偏慢（可能是 cache miss 或轻度 IO）
- `1ms ~ 10ms`：明显慢（通常是磁盘 IO 或网络延迟）
- `>10ms`：瓶颈（磁盘寻道、网络往返、锁竞争）

## 2. 汇总统计模式：-c

`-c` 不做逐行输出，程序结束时打印一张统计表。这是性能分析的**首选入口**。

```bash
# 针对一个完整的命令
strace -c find /usr -name "*.h"

# 附着到运行中的进程（等几秒后 Ctrl+C）
strace -c -p $(pgrep nginx)
```

输出示例：

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 58.23    0.583212         112       5200           epoll_wait
 20.11    0.201322           5      40212           writev
 12.45    0.124512           3      41000           readv
  5.21    0.052132          10       5200           accept4
  2.00    0.020010           2      10000           sendfile64
------ ----------- ----------- --------- --------- ----------------
100.00    1.005318                 101612         total
```

**三步解读法**：

1. **看 `% time` 最高的行**：哪个 syscall 占用时间最多？
2. **看 `usecs/call` 是否异常**：平均每次调用耗时是否合理？
3. **看 `calls` 是否过多**：调用次数是否异常高？

## 3. 高级统计技巧

### 3.1 -w 按耗时排序

默认 `-c` 的输出按调用名字典序排列。`-w`（strace 4.26+）改为按总耗时从高到低排序：

```bash
# 不加 -w：按字母顺序
strace -c myapp
# brk, close, exit_group, mmap, openat, read, write...

# 加 -w：按耗时降序，瓶颈一目了然
strace -c -w myapp
# write     45.23%
# futex     30.12%
# read      15.11%
# ...
```

**最佳实践**：总是把 `-c -w` 组合使用。

### 3.2 %wall 只看耗时调用

strace 5.0+ 支持 `-e trace=%wall`，只显示超过一定阈值耗时的调用。配合 `-T` 使用：

```bash
# 自定义过滤：awk 找出 >500 微秒的调用
strace -T -e trace=all myapp 2>&1 | awk -F'[<>]' '$2+0 > 500 {print $0}'

# 只看某类调用中的慢操作
strace -T -e trace=file myapp 2>&1 | awk -F'[<>]' '$2+0 > 1000 {print}'
```

### 3.3 后处理脚本分析

对于复杂的场景，可以先把 strace 输出写到文件，再交给脚本分析。

**按耗时排序前 10 的 syscall**：

```bash
strace -T -o /tmp/raw.log myapp
# 提取所有耗时，按耗时降序
grep -oP '<\K[0-9.]+(?=>)' /tmp/raw.log | sort -rn | head -10
```

**找出最耗时的 5 个文件操作**：

```bash
grep 'openat\|read\|write' /tmp/raw.log | \
  awk -F'[<>]' '{print $2, $0}' | sort -rn | head -5
```

**统计每秒系统调用速率**：

```bash
strace -tt -o /tmp/time.log myapp
# 统计每秒调用的数量
awk '{print substr($1,1,8)}' /tmp/time.log | sort | uniq -c
```

## 4. Syscall 耗时分布详解

不是所有耗时长都意味着瓶颈。不同系统调用的"正常"范围完全不同。

### 文件 IO

| 耗时范围 | 判断 | 说明 |
|----------|------|------|
| < 10 微秒 | 极快 | 数据在 page cache 中命中 |
| 10~100 微秒 | 正常 | 轻微磁盘活动或 metadata 操作 |
| 100 微秒 ~ 10 毫秒 | 慢 | 磁盘寻道或小块随机读 |
| 10~50 毫秒 | 很慢 | HDD 随机读或网络文件系统 |
| > 50 毫秒 | 极慢 | 磁盘故障、NFS 挂死、IO 拥堵 |

### 网络 IO

| 调用 | 正常范围 | 说明 |
|------|----------|------|
| `connect` | < 1ms（本地）/ < 100ms（远程） | 超过 500ms 说明网络有问题 |
| `sendto` / `write` | < 10 微秒 | 内核拷贝数据到 socket buffer 而已 |
| `recvfrom` / `read` | < 10 微秒 | 如果等了很久，对端发得慢 |
| `poll` / `select` / `epoll_wait` | 由超时决定 | 超时=30000ms 时等满 30s 也是正常的 |
| `accept` | < 1 微秒 | 连接已经在队列里了 |

### 锁与同步

| 调用 | 正常范围 | 说明 |
|------|----------|------|
| `futex` (锁) | < 1 微秒 | 快速用户态锁（无竞争） |
| `futex` (等待) | 取决于持锁时间 | 如果平均 > 1ms，锁竞争严重 |
| `sched_yield` | < 1 微秒 | 每次调用很快，但大量调用说明忙等 |
| `nanosleep` | 由定时器精度决定 | 如果比请求的睡眠时间长，说明调度延迟 |

### 内存管理

| 调用 | 正常范围 | 说明 |
|------|----------|------|
| `brk` | < 1 微秒 | 堆扩展通常很快 |
| `mmap` (小块) | 1~5 微秒 | 创建匿名映射 |
| `mmap` (大文件) | 取决于文件大小 | 文件映射本身不耗时，缺页时才慢 |
| `mprotect` | < 2 微秒 | 修改页保护属性 |

## 5. 只看耗时操作：过滤技巧

```bash
# 只看文件 IO 耗时（磁盘瓶颈）
strace -c -e trace=file myapp

# 只看网络相关（延迟/丢包）
strace -c -e trace=network,connect,sendto,recvfrom myapp

# 只看内存映射（mmap 太多可能内存碎片）
strace -c -e trace=mmap,brk,mprotect myapp

# 只看锁相关（竞争问题）
strace -c -e trace=futex,lock,flock myapp

# 只看进程管理（fork/clone 开销）
strace -c -e trace=process myapp
```

**组合 `-T` + 类别过滤 + awk 阈值**：

```bash
# 只看文件操作中 > 1ms 的调用
strace -T -e trace=file myapp 2>&1 | awk -F'[<>]' '$2+0 > 1000 {print}'
```

## 6. 时序分析：两次调用之间的时间

`-tt` 提供微秒级精度的时间戳，可以看到**调用之间的间隔**：

```bash
strace -tt -T myapp 2>&1 | grep -E "(openat|read|write)"
```

```
10:00:01.000123 openat(..., "config.json", ...) = 3 <0.000045>
10:00:01.000456 read(3, ..., 4096) = 4096 <0.000320>
                                    ← 配置读取花了 0.3ms，正常
10:00:05.023456 openat(..., "bigfile.bin", ...) = 4 <0.000050>
10:00:05.452331 read(4, ..., 65536) = 65536 <0.428925>
                                    ← 429ms 读大文件，瓶颈
10:00:05.452335 read(4, ..., 65536) = 65536 <0.000002>
                                    ← 第二次被 cache 了，2 微秒
```

**时序分析的两种模式**：

1. **Syscall 内部耗时**：`<0.428925>` 说明这个 read 本身花了 429ms（磁盘真正在读取）
2. **Syscall 之间耗时**：从 `10:00:01.000456` 到 `10:00:05.023456` 间隔了 4 秒。这段时间**用户态在计算或等待**。如果这里没有系统调用，那说明 CPU 在做纯计算。

```bash
# 统计 syscall 间的时间间隔
strace -tt -o /tmp/s.log myapp
awk 'NR>1 {printf "%.6f\n", $1 - prev} {prev=$1}' /tmp/s.log | \
  sort -rn | head -10
```

## 7. 常见性能模式解读

某些 syscall 的组合和分布模式直接指明了某类问题。识别这些模式是 strace 性能分析的核心技能。

### 7.1 大量小 read / write（buffer 太小）

**特征**：`strace -c` 显示 `read` 和 `write` 调用次数极多，但每次读写数据量很小（eg. 每次 1 字节）。

```bash
strace -c -p <PID>
```

```
calls   syscall
51200   read       ← 5 万次，但每次只读了 1 字节
40212   writev
```

**单独看几行**：

```
read(3, "H", 1) = 1   ← 每次只读 1 字节！
read(3, "e", 1) = 1
read(3, "l", 1) = 1
read(3, "l", 1) = 1
read(3, "o", 1) = 1
```

**根因**：程序用了逐字节读写（比如 `fgetc()` 默认不缓冲，或设置了 `_IONBF`）。每次读一个字节触发一次系统调用，开销巨大。

**方案**：

```bash
# C：setvbuf(fp, NULL, _IOFBF, 8192);  // 设置缓冲区
# Python：用 open('file', 'r', buffering=8192)
# Java：用 BufferedInputStream
```

**正常 vs 异常的量化对比**：

```bash
# 异常：8KB 文件，1024 次 read（每次 8 字节）
strace -c cat smallfile
# calls=1024, usecs/call=1, total=1.0ms

# 正常：8KB 文件，1 次 read（每次 8192 字节）
strace -c cat bigfile
# calls=1, total=0.01ms
```

同样是读 8KB，buffer 太小导致 1000 倍的系统调用数量。虽然每次调用只花 1 微秒，但上下文切换累积起来可观的性能损失。

### 7.2 poll / select / epoll 高耗时（等待事件）

**特征**：`-c` 显示 `poll` / `select` / `epoll_wait` 占总时间比例很高。

```
  % time     seconds  usecs/call     calls    syscall
  ------ ----------- ----------- --------- ----------------
  95.00    9.500000         950      10000    epoll_wait
```

**关键判断**：看 `usecs/call` 和超时参数的关系。

```bash
# 正常的等待
epoll_wait(3, [], 128, 30000) = 0 <30000.1>  ← 等满了 30 秒超时
# usecs/call = 30000 微秒 = 30 毫秒，程序在空闲等待，正常

# 有事件
epoll_wait(3, [{events=EPOLLIN, data={...}}], 128, -1) = 1 <2.3>
# 等 2.3 微秒就有事件了，正常

# 异常：设了很短超时，不断返回
epoll_wait(3, [], 128, 0) = 0 <0.001>
epoll_wait(3, [], 128, 0) = 0 <0.001>
epoll_wait(3, [], 128, 0) = 0 <0.001>
# 超时 0 微秒，每次都立即返回。这叫 busy polling，CPU 被白白浪费
```

**根因**：超时参数设得太短（或设为 0），导致 epoll_wait 不会阻塞，变成了轮询。

**方案**：检查 epoll 超时设置。通常用 `-1`（无限等待）或一个合适的时间（如 50ms），而不是 0。

### 7.3 sched_yield 大量调用（忙等）

**特征**：`strace -c` 显示 `sched_yield` 调用次数极高，且 `% time` 占比很高。

```
  % time     seconds  usecs/call     calls    syscall
  ------ ----------- ----------- --------- ----------------
  99.00    9.900000           1  9900000    sched_yield
```

990 万次 / 秒，每次只要 1 微秒，但这意味着进程**每秒有 99% 的时间在让出 CPU 然后立即被重新调度**，典型的忙等（busy loop）。

**常见原因**：

1. 用户态自旋锁（spinlock）竞争激烈
2. `while(1) { sched_yield(); if(ready) break; }` 模式
3. 旧式用户态线程调度器
4. 某些虚拟机 Guest 的空转实现

**根因**：程序应该用条件变量或 futex 等待事件，而不是不断轮询。

**方案**：

```c
// 错的：忙等
while (!data_ready) {
    sched_yield();
}

// 对的：用条件变量等待
pthread_mutex_lock(&lock);
while (!data_ready) {
    pthread_cond_wait(&cond, &lock);  // 阻塞不消耗 CPU
}
pthread_mutex_unlock(&lock);
```

### 7.4 futex 大量调用（锁竞争）

**特征**：`-c` 显示 `futex` 调用次数很高，且 `usecs/call` 明显偏大。

```
  % time     seconds  usecs/call     calls    syscall
  ------ ----------- ----------- --------- ----------------
  80.00    8.000000         800      10000    futex
```

每次 `futex` 平均 800 微秒。`futex` 在无竞争时应该 < 1 微秒。800 微秒说明**线程之间在激烈竞争锁**。

**进一步分析**：看 futex 的参数

```bash
strace -e trace=futex -T -p <PID>
```

```
futex(0x7f..., FUTEX_WAIT, ..., {tv_sec=0, tv_nsec=20000000}) = 0 <2.345>
futex(0x7f..., FUTEX_WAIT, ..., {tv_sec=0, tv_nsec=20000000}) = 0 <1.890>
futex(0x7f..., FUTEX_WAKE, 1) = 1 <0.001>
```

大量 `FUTEX_WAIT` 且耗时长 → 线程在等锁释放。

**根因**：锁粒度太粗、临界区太大、或锁的顺序导致死锁/活锁。

**方案**：

```bash
# 用 perf 看锁的分布
perf record -e sched:sched_stat_runtime -g -p <PID>
perf report

# 使用线程分析工具
valgrind --tool=drd ./myapp  # 检测锁竞争
# 或
heaptrack ./myapp             # 看内存分配
```

**代码层面**：

```c
// 错的：锁覆盖了太长的操作
pthread_mutex_lock(&lock);
read_data_from_file();      // 磁盘 IO 时间很长
process_data();
write_result();
pthread_mutex_unlock(&lock);

// 对的：只锁必要部分
read_data_from_file();      // 无锁
pthread_mutex_lock(&lock);
process_data();
pthread_mutex_unlock(&lock);
write_result();             // 无锁
```

### 7.5 mmap 频繁调用（内存分配问题）

**特征**：大量 `mmap` / `munmap` / `brk` 调用。

```
  % time     seconds  usecs/call     calls    syscall
  ------ ----------- ----------- --------- ----------------
  30.00    3.000000          30     100000    mmap
  25.00    2.500000          10     250000    munmap
```

**解读**：

- 10 万次 `mmap`，25 万次 `munmap` → 程序在不断地分配和释放内存
- 每次 30 微秒 / 10 微秒，累积时间 5.5 秒
- 对比：单次 `brk` 扩堆只要 < 1 微秒

**根因**：

1. 频繁创建和销毁大对象（每个大对象走 `mmap`）
2. 自定义内存分配器行为异常
3. 线程频繁创建销毁（每线程栈走 `mmap`）
4. JIT 编译器频繁编译/释放代码页

**解决方案**：

```bash
# 检查是否是 glibc 的 mmap 阈值问题
# 小内存走 brk，大内存走 mmap。默认阈值 128KB
export GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072

# 检查线程创建频率
strace -e trace=clone -c -p <PID>
# 如果 clone 也很多，说明线程频繁创建销毁
```

**代码层面**：

```cpp
// 错的：每次分配大对象
for (int i = 0; i < 100000; i++) {
    auto* obj = new BigObject();      // 可能触发 mmap
    delete obj;                       // 触发 munmap
}

// 对的：对象池复用
ObjectPool<BigObject> pool;
for (int i = 0; i < 100000; i++) {
    auto* obj = pool.acquire();
    pool.release(obj);
}
```

## 8. strace + perf 组合

这是最强大的性能分析组合。**strace 看内核态（syscall），perf 看用户态（CPU热点）**。

### 方法论

1. **strace -c** 先看系统调用分布
2. 如果系统调用层面有瓶颈 → 定位具体调用，分析根因
3. 如果系统调用层面正常（调用少且快） → CPU 瓶颈在用户态 → 上 perf

### 找 CPU 热点函数

```bash
# 采样 CPU 热点
perf record -F 99 -p <PID> -g -- sleep 30
perf report -g graph --no-children

# 实时看热点（不需要 record）
perf top -p <PID>
```

### 关联 syscall 和代码路径

```bash
perf record -e syscalls:sys_enter_read -ag -p <PID> -- sleep 10
```

这会在每次 `read` 系统调用时记录调用栈。`perf report` 能告诉你谁在调用 `read`，哪个函数触发了磁盘 IO。

### 实战示例

```bash
# 程序慢，先用 strace
strace -c -p 12345
# 输出显示系统调用很少，epoll_wait 占了 90% 时间
# 说明不是 syscall 层面的问题

# 上 perf
perf top -p 12345
# 发现 sscanf() 占 60% CPU
# 进一步看是想太多了。某个日志解析函数在热点路径上反复解析大量数据
```

### 组合判断表

| strace 结果 | perf 结果 | 结论 |
|-------------|-----------|------|
| 大量 read/write（慢） | 热点在 IO 函数 | 磁盘/网络 IO 瓶颈 |
| 大量 futex（慢） | 热点在锁操作 | 锁竞争 |
| 少量 syscall | 热点在计算函数 | CPU 计算瓶颈 |
| 大量 sched_yield | 热点在自旋等待 | 忙等问题 |
| 大量 epoll_wait（短超时） | 热点在事件循环 | busy polling |

## 9. strace + tcpdump 组合

当 `strace -e trace=network` 发现网络相关调用异常（connect 慢、sendto 慢、recvfrom 慢），但不知道网络包层面发生了什么。

### 分工

| 层 | 工具 | 能看到的 |
|----|------|----------|
| 应用层系统调用 | strace | connect/sendto/recvfrom 的参数和返回值、耗时 |
| TCP/IP 协议栈 | tcpdump | 三次握手细节、重传、窗口、拥塞控制 |
| 物理层/网络 | ping/mtr/iperf | 延迟、丢包、带宽 |

### 实战：查 "connect 慢"

**strace 发现**：

```bash
strace -T -e trace=connect curl https://example.com
# connect(4, ...) = 0 <2.345678>  ← 2.3 秒！
```

2.3 秒的 connect，很慢。但 strace 只能告诉你"connect 花了 2.3 秒"，不能告诉你为什么。

**tcpdump 补全**：

```bash
# 同时抓包
tcpdump -i eth0 -w /tmp/connect.pcap port 443
```

分析抓包文件：

```
# 用 tshark 看交互时间
tshark -r /tmp/connect.pcap -Y "tcp.port==443" -T fields \
  -e frame.time_relative -e tcp.flags.syn -e tcp.flags.ack

0.000000  SYN            ← 发送 SYN
0.500001  SYN+ACK        ← 0.5 秒后收到（正常应该在 1ms 内）
0.500002  ACK            ← 三次握手完成
# 但 connect 等了 2.3 秒！

# 再看后续：
2.300000  TLS Client Hello  ← 等了 1.8 秒才发！
```

问题不在 TCP 连接本身（三次握手只花了 0.5ms），而是在**连接建立后、发送第一个请求之前的这段时间**。tcpdump 显示出 1.8 秒的空白。这个时间可能是：

- DNS 解析
- TLS 协商（如果先解析证书）
- 代理协商
- 应用层的某些初始化

再配合 strace 看这 1.8 秒发生了什么：

```bash
# 精确时序
strace -tt -T -e trace=network curl https://example.com
```

### 另一个案例：大量重传

**strace**：

```
sendto(4, ..., 1450, 0, ...) = 1450 <10.234>  ← 10 秒才返回
```

sendto 花了 10 秒，说明内核的发送缓冲区满了，调用被阻塞直到缓冲区有空间。

**tcpdump**：

```
# 发现大量 TCP 重传
tcpdump -i eth0 port 80 -v | grep "retransmission\|dup ACK"
# 11:23:45.678901 IP (tos 0x0, ttl 64, ...) 10.0.0.1.80 > 10.0.0.2.54321: Flags [P.], seq 1:1449, ack 1, ... [TCP Retransmission]
```

网络质量差，大量丢包，导致内核缓冲区积压，sendto 阻塞。

## 10. strace + lsof + /proc 文件系统

这三个工具配合可以快速度量一个进程的资源使用画像。

### 快速进程画像

```bash
# PID=12345, 目标进程

# 1. lsof - 看打开的文件
lsof -p 12345
# 看看有没有大量重复打开的文件（FD 泄漏）
# 看看有没有文件处于异常状态

# 2. /proc - 看内核视角的信息
ls -la /proc/12345/fd/          # 所有文件描述符
cat /proc/12345/limits          # 资源限制
cat /proc/12345/status          # 状态、内存、信号
cat /proc/12345/io              # IO 统计（读写字节数）
cat /proc/12345/syscall         # 当前正在执行的 syscall
cat /proc/12345/wchan           # 当前在内核的什么函数中
cat /proc/12345/stack           # 内核调用栈

# 3. strace - 看动态行为
strace -c -p 12345              # 调用频率统计
```

### 实战：/proc/syscall 的妙用

```bash
# 进程看起来卡住了，看它卡在哪个 syscall
cat /proc/12345/syscall
# 输出：2 0x7f... 0x7f... 0x20000 0x0 0x0 0x0 0x0 0x0 0x7f...
#        ^ syscall 号
```

对照 `/usr/include/asm/unistd_64.h`：

| 编号 | Syscall | 含义 |
|------|---------|------|
| 0 | read | 读文件/socket |
| 1 | write | 写文件/socket |
| 2 | open | 打开文件 |
| 9 | mmap | 内存映射 |
| 35 | nanosleep | 睡眠 |
| 40 | sendfile | 零拷贝发送 |
| 202 | futex | 锁操作 |
| 231 | exit_group | 退出 |

也可以用工具一键翻译：

```bash
# 用 strace 翻译
strace -p 12345 2>&1 | head -1
# 或者用脚本
awk '/syscall_number/{print $2}' /proc/12345/syscall | \
  xargs -I {} grep -w "{}" /usr/include/asm/unistd_64.h
```

### 实战：磁盘 IO 延迟

```bash
# 先看 /proc 中的 IO 统计
cat /proc/12345/io
# rchar: 123456789   ← 读的字节数（包括 page cache 命中）
# wchar: 987654321   ← 写的字节数
# read_bytes: 50000000  ← 实际磁盘读取（page cache 未命中）
# write_bytes: 80000000 ← 实际磁盘写入

# 如果 read_bytes << rchar，说明 page cache 命中率高
# 如果 read_bytes ≈ rchar，说明频繁磁盘 IO

# 然后用 strace 确认
strace -c -e trace=file,read,write -p 12345
# 看 read/write 的调用次数和耗时
```

## 11. 完整长案例：从发现到根因

### 问题

某 Web 服务（Nginx 反向代理 + 后端 Java 应用）上线新版本后，P99 延迟从 50ms 飙升到 2 秒。

### 第一轮排查：是不是系统调用级别的问题？

```bash
# 找后端 Java 进程
jps -l
# 12345 com.example.MyApp

# 附着 strace 统计 30 秒
strace -c -w -p 12345 &
sleep 30
kill %1
```

输出：

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 40.00   12.000000         800      15000           futex
 30.00    9.000000          90     100000           read
 20.00    6.000000          60     100000           write
  5.00    1.500000          15     100000           epoll_wait
------ ----------- ----------- --------- --------- ----------------
100.00   30.000000                315000         total
```

**初步判断**：

- `futex` 占 40%，每次 800 微秒 → **锁竞争！！**
- `read` / `write` 各 10 万次，每次 60~90 微秒 → 偏高但不算离谱
- `epoll_wait` 只占 5% → 大部分时间不在等网络

### 第二轮：看锁的细节

```bash
strace -e trace=futex -T -p 12345 2>&1 | head -20
```

```
futex(0x7f1234567890, FUTEX_WAIT, 1234, {tv_sec=0, tv_nsec=50000000}) = 0 <3.456>
futex(0x7f1234567890, FUTEX_WAIT, 1235, {tv_sec=0, tv_nsec=50000000}) = 0 <2.890>
futex(0x7f1234567890, FUTEX_WAIT, 1236, {tv_sec=0, tv_nsec=50000000}) = 0 <4.123>
futex(0x7f1234567890, FUTEX_WAKE, 1) = 1 <0.001>
```

多个线程（1234, 1235, 1236）在**同一个 futex 地址**上等待，等 3~4 毫秒。锁竞争严重。

### 第三轮：关联到代码

用 perf 看谁在等锁：

```bash
perf record -e futex:* -ag -p 12345 -- sleep 30
perf report -g graph
```

perf 报告显示热点在 `com.example.MyApp.processRequest()` 中的某个 `synchronized` 块。再看代码：

```java
public class DataProcessor {
    // 这是一个 class-level 锁！
    public static synchronized void process(Request req) {
        // 1. 读数据库（网络 IO，2~10ms）
        Data data = db.query(req.getId());
        // 2. 写日志（文件 IO）
        log.write("processing: " + req.getId());
        // 3. CPU 计算
        Result r = transform(data);
        // 4. 再写数据库
        db.save(r);
    }
}
```

**问题**：`static synchronized` 锁了类级别。所有请求串行通过这个函数。数据库查询（网络 IO）和日志写入（文件 IO）都在锁里面，导致其他线程只能等着。

### 第四轮：验证

```bash
# 看看同一时刻有多少线程被阻塞
# 用 jstack
jstack 12345 | grep -c "BLOCKED"
# 输出：15
# 15 个线程被阻塞在锁上！
```

### 解决方案

```java
public class DataProcessor {
    private static final Object lock = new Object();

    public void process(Request req) {
        // 1. 无锁读数据库
        Data data = db.query(req.getId());

        // 2. 只在必要的地方加锁
        Result r;
        synchronized (lock) {
            r = transform(data);   // 只保护这步
        }

        // 3. 无锁写数据库和日志
        db.save(r);
        log.write("processed: " + req.getId());
    }
}
```

### 修复后验证

```bash
# 再跑 strace 30 秒
strace -c -w -p 12345 &
sleep 30
kill %1
```

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 40.00    4.000000          40     100000           read
 30.00    3.000000          30     100000           write
 15.00    1.500000          10     150000           epoll_wait
  5.00    0.500000          33      15000           futex
------ ----------- ----------- --------- --------- ----------------
100.00   10.000000                365000         total
```

**改善**：

- `futex` 耗时从 12 秒降到 0.5 秒
- 总 syscall 耗时从 30 秒降到 10 秒（三倍提升）
- P99 延迟从 2 秒降到 60 毫秒

### 案例总结

```
症状: P99 从 50ms 飙升到 2s
  ↓ strace -c -w
发现: futex 占 40%，每次 800us
  ↓ strace -e trace=futex -T
确认: 大量 FUTEX_WAIT，同一地址，等待 3~4ms
  ↓ perf record -e futex:* -ag
定位: static synchronized 方法，锁粒度过大
  ↓ 修复: 缩小锁范围，IO 操作移出临界区
结果: P99 回到 60ms
```

## 12. strace 的局限与互补工具

| 工具 | 层次 | 适合 | 不适合 |
|------|------|------|--------|
| **strace** | 系统调用 | IO 瓶颈、错误码、文件访问、网络延迟、锁竞争 | CPU 热点、内存错误、代码逻辑 |
| **perf** | CPU 指令 / 硬件事件 | CPU 热点、cache miss、分支预测、IPC | syscall 参数细节、错误原因 |
| **perf top** | 实时热点 | 哪个函数吃 CPU | 运行时行为跟踪 |
| **flamegraph** | 可视化 CPU 栈 | 性能分布可视化 | 细粒度调试 |
| **ltrace** | 库函数 | 库调用次数和耗时（eg. malloc/free 频率） | 内核行为 |
| **iostat** | 磁盘设备 | 磁盘吞吐、队列深度、await、svctm | 单进程 IO 行为 |
| **tcpdump** | 网络包 | 重传、延迟分布、握手细节、窗口分析 | 应用层语义 |
| **lsof** | 文件描述符 | 查看打开的文件、FD 泄漏 | 动态调用行为 |
| **/proc** | 内核状态 | 当前 syscall、内存、IO 统计、限制 | 随时间变化的行为 |
| **valgrind** | 内存调试 | 内存泄漏、未初始化内存、FD 泄漏 | 性能（慢 20~50 倍） |
| **bpftrace** | 内核动态跟踪 | 自定义内核探针、任意事件 | 学习曲线陡峭 |

### 工具选择流程

```
性能问题
│
├─ CPU 高？
│   ├─ strace -c → 系统调用多 → 分析 syscall 层面
│   └─ strace -c → 系统调用少 → perf top → 看用户态热点
│
├─ IO 慢？
│   ├─ 磁盘：strace -T → iostat → 确认磁盘设备
│   ├─ 网络：strace -T → tcpdump → 确认网络包延迟
│   └─ 锁：strace -e trace=futex → perf futex 事件
│
├─ 内存？
│   ├─ strace -e trace=memory → valgrind / heaptrack
│   └─ /proc/PID/smaps → 看内存分布
│
└─ 程序崩溃？
    ├─ strace → 看最后的 syscall 和信号
    ├─ dmesg → 看内核 OOM/segfault 信息
    └─ coredump → gdb 看堆栈
```

## 13. 性能分析判断路径

这是一张从 strace 输出到问题定位的决策树：

```
高 CPU？
├── strace -c → 大量 sched_yield → 用户态忙等，查自旋锁/轮询
├── strace -c → 大量 futex (WAIT) → 锁竞争，查临界区
├── strace -c → 大量 read/write (小数据量) → buffer 太小
├── strace -c → 大量 clone → 线程频繁创建销毁
├── strace -c → 大量 mmap/munmap → 内存分配频繁
├── strace -c → 大量 epoll_wait (超时=0) → busy polling
└── strace -c → 调用很少 → CPU 在用户态计算 → 上 perf

慢响应？
├── strace -T → connect/poll > 100ms → 网络延迟
├── strace -T → read > 50ms → 磁盘慢（HDD 随机读 / NFS 延迟）
├── strace -T → read/write 多但每次 < 10us → 调用次数过多（buffer 问题）
├── strace -T → futex > 100us → 锁竞争
├── strace -T → 都是微秒级 → 瓶颈不在 syscall → 上 perf
└── strace -tt → 调用间有长间隔 → 用户态计算耗时

FD 泄漏？
├── strace -e trace=open,openat,close → 看 open 和 close 是否匹配
├── lsof -p PID | wc -l → 看 FD 总量
└── ls /proc/PID/fd → 看哪些文件被打开了
```
